# Resource audit 5: codec and Discord packet path

This audit checked decoder/filter/Opus ownership and the Discord DAVE/RTP packet path against
baseline `1980846a515cd650958cef3b85c8864d93d7960f`. It retains
the phase 2/3 filter-thread cap, resampler output reuse, bounded PCM staging, Opus packet scratch,
pre-skip handling, and passthrough behavior. It does not change the Opus default (complexity 9),
RTP pacing, packet queue limits, DAVE readiness, transport encryption, or media quality settings.

## Findings and change

`RtpSender` already reused a 1200-byte datagram buffer for the RTP packet and transport cipher,
but `DaveProtocol::encrypt_opus` returned a newly owned `Vec` for every DAVE-encrypted Opus packet.
The sender then copied that payload into its reused datagram. `davey 0.2.0` also exposes
`DaveSession::encrypt_into`, so the DAVE output can be written into the sender-owned allocation.
The sender now clears and reuses that buffer for DAVE output, shifts the payload in place to leave
the RTP header prefix, writes the header, and seals the same datagram with the existing transport
cipher. This removes one Rust-allocator allocation and its intermediate payload copy per packet.
The overlap-safe in-buffer shift remains necessary to prepend the header.

A DAVE frame can be larger than the UDP packet limit before the final encrypted size is known. The
oversize path now drops any grown `Vec` and restores the normal 1200-byte capacity, so a rejected
packet cannot leave a long-lived sender retaining an oversized buffer. The regression also checks
that rejecting that packet leaves sequence, timestamp, and nonce unchanged for the next valid send.

The ownership audit found no other confirmed leak or avoidable copy worth changing in the assigned
decoder, filter, resampler, Opus, DAVE, RTP, cipher, or sender-queue paths. Existing graph ownership
is exclusive during setup/use; decoded frame references are scoped to their source frames; the
resampler context is exclusively accessed; and packet queues remain bounded. No new `unsafe` Rust
was added. Filter and decoder changes were rejected because the reviewed paths already reuse their
native contexts/storage or have an ownership reason for the copy.

## Opus complexity and quality

The deterministic fixture is 60 seconds of 48 kHz stereo signed 16-bit PCM, generated by
`resource-audit-5.py`; SHA-256 is
`eb71e54d961bd694a1957daebc47291bb00282c439d0f529c4583e314df62614`. It combines layered changing
tones and deterministic noise. Each quality run used 128 kb/s VBR and captured Remedia's encoded
packets, decoded them with `opus2`, aligned the 312-sample encoder lookahead, and compared the
resulting samples to the input. Each run produced 3000 20 ms packets and exactly 2,880,000 media
samples. The compared range contains 2,879,688 samples per channel; segment SNR uses 100 ms windows.

| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 5 | 8.1674 (8.1339–8.1908) | 8.0622 (7.8345–8.1830) | 0.2145 (0.2119–0.2381) | 1.9682 (1.9043–1.9909) | 20.9673 dB | 20.0459 dB | 19.3356 dB |
| 6 | 8.2115 (7.9287–8.4051) | 8.2012 (7.8731–8.3104) | 0.2461 (0.1985–0.2806) | 1.9980 (1.8348–2.0396) | 20.9673 dB | 20.0459 dB | 19.3356 dB |
| 9 | 12.2208 (12.2068–12.3965) | 11.9915 (11.9358–11.9971) | 0.3021 (0.2972–0.3602) | 2.9382 (2.8094–2.9648) | 21.2326 dB | 20.2956 dB | 19.7034 dB |

CPU figures are medians and min/max ranges from three fresh-process runs. Each session consumed the
same 60-second file without pacing or passthrough; 32 sessions therefore processed 1920 seconds
of audio and 96,000 packets. The full before/after matrix is in
`resource-audit-5-complexity.jsonl`; sample and packet totals matched in every run. The core
benchmark is unchanged by the Discord edit, and the before/after CPU ranges overlap in most cases,
so those small deltas are not evidence of a packet-path CPU gain. Complexity 9 used about 49% more
CPU than complexity 5 at 32 concurrent sessions on this fixture. Complexity 5 and 6 produced
identical SNR here, while complexity 9 was about 0.27 dB higher overall and 0.25 dB higher at the
segment p10.

The separate before/after quality runs also matched exactly at each complexity. Since the
implementation does not touch the core encoder, this is a correctness/measurement check rather
than a claim of changed codec quality.

These are objective sample-domain measurements of one synthetic fixture. They do not establish
subjective quality or generalize to speech, silence, transients, or a broad set of program music.
They do not justify reducing encoder complexity. The default remains 9.

## DAVE/RTP packetization measurement

The ignored packetization benchmark warms each sender with 1000 packets and then measures 50,000
90-byte Opus packets under an established test DAVE group. It uses the same release profile and
dependencies for before/after builds. The per-thread counting global allocator only observes Rust
allocator calls; it does not count native allocations made by FFmpeg, Opus, DAVE, or the OS.

| Encryption mode | Before allocations / packet | After allocations / packet | Before ns / packet median (range) | After ns / packet median (range) |
| --- | ---: | ---: | ---: | ---: |
| AES-256-GCM | 1.00 | 0.00 | 948 (938–971) | 932 (927–986) |
| XChaCha20-Poly1305 | 1.00 | 0.00 | 1307 (1303–1342) | 1291 (1288–2358) |

There are nine interleaved before/after runs per mode. Both paths still produce decryptable RTP
and DAVE payloads with the expected source Opus bytes. The AES median moved by 1.7% and the
XChaCha median by 1.2%; these differences are within the observed variation, including one
XChaCha outlier, so no CPU-speedup claim is made. The validated gain is elimination of the one
per-packet Rust allocation in this packet-construction path. The payload still moves once within
the reused buffer.

## Heap and process observations

An 8-session, one-run-per-complexity allocation pass processed 480 seconds of audio and 24,000
packets for each case. The Rust allocator reported 35,574 allocations and about 192,157,248 bytes
allocated over each run, with 358,930–359,237 bytes peak live Rust heap. These totals are nearly
identical across complexity 5/6/9 because the encoder setting changes its work rather than this
benchmark's Rust-side packet/session allocation pattern.

`wait4` process peak RSS was 18.53–19.09 MiB across those six single-run samples. It includes Rust,
FFmpeg, Opus, shared libraries, and other process mappings; it is not a native-heap measurement.
The in-process resource sampler observed only 3.33–3.36 MiB footprint and two or three threads in
this short unpaced run. Its one-second sampling can miss short-lived peaks, so it does not replace
the `wait4` peak. RSS and Rust allocator counters answer different questions and should not be
subtracted to infer native heap. The raw rows are in `resource-audit-5-heap.jsonl`.

## Reproduction and verification

The measurement host was Apple M5, 10 logical CPUs, macOS Darwin 27 arm64, Rust/Cargo 1.99.1,
release profile with workspace `lto = "fat"`, and the pinned Cargo lockfile (`davey 0.2.0`,
`opus2 0.4.0`). pkg-config selected Homebrew FFmpeg 9.0.2 (`libavcodec 63.1.102`, `libavfilter
12.1.102`, `libswresample 7.1.102`, and `libswscale 10.1.102`). Use the repo's matching FFmpeg
installation on another machine; these paths are specific to the measurement host.

```sh
export PKG_CONFIG_PATH=/opt/homebrew/opt/ffmpeg/lib/pkgconfig
export LIBRARY_PATH=/opt/homebrew/opt/lame/lib:/opt/homebrew/opt/openssl@4/lib:/opt/homebrew/opt/svt-av1/lib
python3 benchmarks/resource-audit-5.py fixture /tmp/remedia-resource-audit-5/music60.wav --seconds 60
cargo build --release -p remedia-core --example concurrent_playback_benchmark --example resource_audit_5_opus_quality
python3 benchmarks/resource-audit-5.py run --binary target/release/examples/concurrent_playback_benchmark \
  --fixture /tmp/remedia-resource-audit-5/music60.wav --output /tmp/resource-audit-5-after.jsonl --label after --repeats 3
python3 benchmarks/resource-audit-5.py quality --binary target/release/examples/resource_audit_5_opus_quality \
  --fixture /tmp/remedia-resource-audit-5/music60.wav --output /tmp/resource-audit-5-quality.jsonl --label after
cargo test --release -p remedia-discord -- packetization_cost --ignored --nocapture --test-threads=1
```

The raw before/after captures checked in here were taken from release binaries built with the same
lockfile, native libraries, fixture, and benchmark code. On this host, initial linking also needed
a temporary macOS `c++` linker directive because the local static FFmpeg package metadata omitted
it; the directive was only a local build workaround and is not part of the change. No package or
system dependency was installed or modified.

The Rust regression suite verifies zero Rust allocator calls over 100 warmed packets for both
encryption modes, datagram pointer reuse, transport decryption, DAVE decryption back to the source
Opus packet, rejection of oversized datagrams without retained growth, and unchanged RTP timing
and nonce state after a rejected packet. These tests do not exercise a live Discord connection,
network scheduling, another operating system, or native heap accounting.

Raw captures: `resource-audit-5-complexity.jsonl`, `resource-audit-5-heap.jsonl`,
`resource-audit-5-quality.jsonl`, and `resource-audit-5-packetization.jsonl`.
