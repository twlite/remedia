# Discord bot harness

`apps/discord` is a small manual integration app for testing the Node.js
Gateway adapter and native Discord voice sender. It uses discord.js for the
outer bot Gateway and slash commands; `@remedia/node` handles voice joining,
decoding, Opus, DAVE, and outbound transport. It is not a general bot framework
or a media extractor.

## Setup and run

Create `apps/discord/.env` with the bot token and application ID:

```dotenv
DISCORD_TOKEN=your-bot-token
APPLICATION_ID=your-application-id
```

Install the workspace and native dependencies described in the
[Node.js binding setup](/docs/node/bindings#build-prerequisites), then build the
Node addon, register commands, and start the source through `tsx`:

```sh
pnpm install --frozen-lockfile
pnpm --filter @remedia/node build
pnpm --filter discord-app deploy
pnpm --filter discord-app start
```

The Discord application requires the `Guilds` and `GuildVoiceStates` Gateway
intents. It forwards raw Gateway dispatches to Remedia and sends OP 4 through
the discord.js shard that owns the target guild. It does not collect or expose
voice session IDs, tokens, or endpoints.

## Commands

- `/play url:<http-or-https-url>` joins the command user's current voice
  channel and starts the URL. If another track is playing, the URL is appended
  to that server's in-memory queue. Replies use the title from Remedia media
  metadata when available; otherwise they show a sanitized URL.
- `/pause` and `/resume` control the current track and include its title when
  Remedia provided one.
- `/seek seconds:<number>` seeks to a position in seconds and identifies the
  current track when available.
- `/queue list` shows the current item and up to ten upcoming URLs;
  `/queue clear` removes upcoming items but keeps the current track.
- `/loop mode:<off|track|queue>` controls this guild's playback loop. `track`
  repeats the current track after natural completion; `/skip` still advances to
  the next item. `queue` rotates naturally completed and manually skipped tracks
  to the end of the queue. Failed tracks are not repeated. `off` restores normal
  one-pass playback.
- `/skip` stops the current item and starts the next queued URL, showing titles
  when Remedia metadata is available.
- `/nowplaying` shows the Remedia title when available, playback state, and
  a proportional progress bar against the original media duration. Estimated
  source positions are prefixed with `~`; unknown durations do not imply a
  percentage. Its filter field lists active presets in selection order.
- `/stop` stops playback and clears the queue while keeping the voice
  connection open.
- `/disconnect` stops playback, clears the queue, and leaves the voice channel.
- `/filter set <preset>` toggles one of `8d`, `bassboost`, `nightcore`,
  `vaporwave`, `tremolo`, or `vibrato`. An inactive preset is appended to the
  active filters; selecting an active preset removes only it. The remaining
  graphs keep their order, and removing the last preset clears the graph.
  `/filter clear` disables all active graphs, and `/filter list` displays the
  choices and current selection.
- `/volume` reads the current setting; `/volume percent:<0..200>` sets linear
  gain. Zero mutes, 100 is unity, and values above 100 may clip.
- `/nowplaying` also shows the selected loop mode.

The queue belongs to this sample application, not `remedia-core` or
`@remedia/node`. It is held in memory per guild and is lost when the bot exits.
It holds up to 100 upcoming tracks in addition to the current track.
The loop mode is stored per guild, remains selected across tracks and `/stop`,
and resets when the voice session is disconnected. In queue mode, the current
track counts as part of the loop; if it is the only item, it repeats by itself.
Upcoming queue entries have not been opened by Remedia yet, so they display
their sanitized URLs until playback begins and metadata becomes available.
When a track reaches natural end-of-stream, the app advances to the next queued
URL. A track that fails to open or decode is skipped; the failure is retained
in the playback snapshot and shown by `/nowplaying`; the process log reports
the guild without printing the media URL. Commands are
restricted to users currently in the same voice channel as the bot. The bot
does not move an existing session to another channel implicitly; disconnect
first, then issue `/play` from the new channel.

The six names above are convenience presets defined only in `apps/discord`; each
maps to a raw FFmpeg graph passed to the generic Node API. `/filter set` toggles
the selected preset: adding one appends its graph, while toggling it off removes
only that graph and retains the order of other selections. Removing the last
selection follows the same graph-clear path as `/filter clear`. Changes apply
immediately to the active track and carry over to queued tracks and skips.
Filter changes do not change volume, and volume changes do not rebuild the
graph. A disconnect or bot shutdown disposes the guild player and drops both
settings. Engine callers can use arbitrary trusted filtergraphs instead of
these names.

Slash command replies use consistent Remedia embeds, including colored error
embeds when an operation fails. `/nowplaying` formats source time and duration
around a compact progress bar; estimated source positions are prefixed with
`~`.

The app also subscribes to the typed `@remedia/client` session events. It posts
embeds for track start, natural completion, stop and failure; pause, resume,
seek, filter and volume changes; and important voice connection transitions.
Track lifecycle notifications use the `customMetadata` attached to that
playback generation to find the originating text channel. The first `/play`
request that creates a guild queue stores its sendable channel object in that
queue's in-memory metadata, and each playback passes that reference through
Remedia's JavaScript-only `customMetadata`. The reference is not serialized to
Rust or a remote Remedia server. Later requests and queued tracks continue to
notify the original queue channel until the guild session is disconnected and
disposed. Successful control-command acknowledgements are ephemeral to avoid
duplicating the public event messages; queue snapshots remain public. If the
bot cannot send in the retained channel, playback continues and a warning is
written only when `REMEDIA_DEBUG=1`.

Queue operations are serialized per guild. Skip stops and joins the current
playback before opening the next URL while retaining the connected voice
transport. Completion waits are bound to the source generation active when
`wait()` was called, so a delayed completion from an old item cannot clear or
advance a replacement item.

Only direct HTTP(S) media URLs are accepted. The installed FFmpeg libraries
must support the container and codec. There is no search, URL resolution,
playlist import, client stream upload, or file-path command. Displayed URLs
omit query strings and credentials, while the original URL is passed to the
decoder.

`stop` leaves Discord connected so another `/play` can reuse the session.
`disconnect` or process shutdown releases the playback session and native voice
transport. Playback is unpaced by the decoder; the Discord transport schedules
encoded packets in real time. See the [voice output guide](/docs/discord/voice-output)
for Opus, DAVE, transport encryption, and protocol limitations.

This harness is intended for manual integration with a configured bot. The
automated tests use mock sessions and do not establish a live Discord
connection; hosted or live compatibility must be verified separately.
