## Automatic Opus passthrough and PCM mode switching

When the output implements the optional `EncodedOpusOutput` capability (as
`OpusEncoderOutput` does), playback can route compatible source Opus packets
directly to the same packet sink used for encoded PCM. Other outputs remain
PCM-only and keep the regular decoder behavior. `PlaybackSession::processing_mode()`
reports the selected path as `Some(PlaybackProcessingMode::Passthrough)` or
`Some(PlaybackProcessingMode::Transcoding)` after source startup. It is `None`
before a source selects a path. The final selection remains inspectable after
completion.

Passthrough is enabled only when the selected stream is Opus at 48 kHz with a
supported mono/stereo family-zero OpusHead with no output gain and a pre-skip that is
either zero or shorter than one packet and agrees with the container (see
[Opus pre-skip](#opus-pre-skip)), matching channel metadata, no trailing padding, and packet
payloads, durations, and sizes accepted by the output. The packet duration is parsed from the Opus payload.
Packets with FFmpeg skip-sample side data or container duration indicating
trimming fall back to PCM. Active filtergraphs, any gain other than exactly
`1.0`, non-Opus input, and outputs without encoded-Opus support require
transcoding. A seek decodes only the packet that contains the target; see
[Seamless return to packets](#seamless-return-to-packets). Unsupported input is a normal fallback. See [audio decoding](/docs/core/decoding)
for the complete conservative compatibility policy.

If a live filter or gain change cannot initialize the PCM decoder, the active
eligible passthrough path remains running and the filter update returns the
decoder error. The rejected graph is not retained. While playing, a gain change
that switches modes waits for the worker boundary and returns a transition
error. While paused, it stages the gain for resume. These operations can wait
for an in-flight input read or bounded output backpressure, and `stop()` cancels
the wait.

The demuxer stays open across mode changes. On passthrough-to-PCM activation,
the worker constructs the decoder from the selected stream parameters and
replays only a bounded history of up to 140 ms (seven packets) or 512 KiB of preceding Opus
packets. Warm-up output before the exact transition boundary is discarded.
The next unread source packet is then decoded and processed. This policy also
works with one-shot non-seekable streams and does not promise identical
warm-up behavior for every Opus implementation. The history is cleared on
seeking and source replacement.

Returning from PCM to source packets has a second requirement that gain and filter changes do
not satisfy on their own: the encoder's lookahead must be drained first. See
[Seamless return to packets](#seamless-return-to-packets).

When processing requirements are removed, the worker completes pending decoded
frames and any partial encoder PCM before forwarding the next source packet. A remaining partial PCM block is padded to the shortest legal Opus packet
duration, adding at most 119 silent samples per channel, and the native encoder
state is reset before passthrough resumes. Delayed samples still buffered
inside the active filtergraph are discarded at this boundary, matching live
graph replacement behavior.

No source is reopened, no output sink or Discord
sender is replaced, and no seek flush or RTP-generation change occurs. The
output sample position stays contiguous. RTP sequence and timestamp state
remain transport-owned. A short silence or transition artifact is possible,
especially around stateful or time-changing filters, so this is not a guarantee
of sample-perfect seamless audio.

Source-media position, processed PCM output position, and RTP transport time
remain separate. Passthrough packets receive the next contiguous output sample
position rather than inheriting container timestamps. Source timestamps still
drive the media position when available. Time-changing filters determine their
own output sample count. Remedia does not infer a speed ratio from graph text.

For a reproducible unpaced throughput comparison using an Opus file, run:

```sh
cargo run -p remedia-core --example opus_processing_benchmark -- ./media/track.ogg
```

The example reports the selected mode, wall time, delivered duration, packet
throughput, payload bytes, and real-time factor for automatic selection,
forced PCM re-encoding, a light filter, and a tempo filter. It measures an
in-process counting sink, not Discord network latency or peak memory.

## Demuxing and decoder warm-up

Playback sessions with an Opus-capable encoded output can automatically bypass PCM decoding for a
restricted set of compatible source Opus packets. The decoder still owns the same demuxer and
selected stream. It reads compressed packets first and constructs libavcodec and libswresample
contexts only if the session needs PCM. The public `AudioDecoder` pull API continues to initialize
and return PCM as before.

The passthrough path is conservative. It requires an Opus stream with a supported OpusHead (48 kHz,
mono or stereo, family-zero mapping, a pre-skip shorter than one packet that the container and the
OpusHead agree on, and zero OpusHead output gain), matching stream/OpusHead channel counts, no
trailing padding, and complete Opus packets whose
actual duration and output compatibility checks succeed. Packets with skip-sample side data or a container duration shorter than the encoded
Opus packet are decoded instead.

An output may also reject packets that exceed its duration or size
limits. MP3, AAC, Vorbis, trimmed Opus, and any source sent to a PCM-only output use the regular
decode/resample path. Failure of an eligibility check is a normal fallback, not an error.

For a passthrough source that later needs PCM processing, Remedia keeps the open demuxer and replays
a rolling maximum of 140 ms (seven packets) and 512 KiB of preceding Opus packets into a newly initialized decoder. The bounded history is intended to provide decoder warm-up while remaining suitable for non-seekable
inputs. It is not a claim that every possible Opus stream has identical decoder preroll needs.

Decoded warm-up samples before the transition boundary are discarded. The transition never reopens
a URL or restarts a one-shot byte stream. Seeking uses FFmpeg decoding to trim an arbitrary
target precisely, then returns to passthrough at the next packet boundary. See
[RFC 7845](https://www.rfc-editor.org/rfc/rfc7845.html) for Ogg Opus pre-roll and granule-position
semantics.

## Opus pre-skip

Every file written by libopus or FFmpeg carries a **pre-skip** (312 samples, 6.5 ms, for the
encoder's lookahead). RFC 7845 asks a player to discard that many decoded samples at the start of
the stream. Before this support, such a stream was never forwarded as packets: it was decoded and
re-encoded for its whole length.

Remedia now forwards these streams. Discord clients cannot be told to skip samples, so the first
packet is forwarded **unchanged** and the pre-skip is accounted for instead of ignored:

- The first packet is `samples_per_channel` 960 with `media_samples_per_channel` 648. The 312
  pre-roll samples count toward RTP time but not toward media time, so `start_sample` values
  stay contiguous and the reported source position is exact. A client plays exactly what a
  player that ignores pre-skip would play: FFmpeg's own decode, delayed by 312 samples. Tests
  decode Remedia's output with a fresh libopus decoder and compare it with FFmpeg's decode of
  the same file: the audio is identical apart from that delay and decoder rounding.
- The pre-skip is read from the Ogg `skip_samples` side data or, for Matroska/WebM, from the
  codec parameters, and must match the OpusHead. A pre-skip of one packet or more is not modeled
  and keeps the stream on the PCM path.
- Before forwarding, the first packet is decoded once to confirm that the pre-skip region is
  **encoder delay**: either no louder than about -60 dBFS, or at most 35% of the peak of the audio
  that follows in the packet. An abrupt start produces pre-echo of about -30 dB relative to the
  onset, which is the same pre-echo the PCM path's own encoder emits. A stream whose "pre-roll" is
  as loud as its audio was mislabeled and is decoded, where FFmpeg trims it exactly.
- The last packet of such a file normally carries end trimming and is therefore decoded and
  re-encoded, as before.

Streams whose pre-skip is 0 are unaffected. The duration of an Ogg Opus file excludes its
pre-skip, so it equals the length of the audio a player decodes.

## Seamless return to packets

A fresh libopus encoder delays its output by its 312-sample lookahead; this is why Opus streams
carry a pre-skip of that size. Re-encoded PCM therefore lags the packet timeline by 312 samples,
and a client decoder that is handed an original packet right after re-encoded audio starts cold:
measured against FFmpeg's decode, switching immediately left a hole at the seam and a residual of
about -1 dB that took eight packets to fall below -40 dB.

Wherever Remedia switches from re-encoded PCM back to source packets after a **seek** or a
crossfade **promotion**, it therefore:

1. requires the stream's pre-skip to equal the encoder lookahead (312, true of libopus and FFmpeg
   output); any other stream keeps decoding after a seek or promotion, as it did before;
2. keeps the encoder running for at least six 20 ms frames, so a freshly reset encoder has
   settled and the client's decoder state has converged on the re-encoded audio;
3. tracks the encoder's partial frame. After a seek the first frame starts on the 20 ms grid with
   fewer than 20 ms of leading silence that is not media (`align_encoder_frames`); the packet
   reports the shorter media duration;
4. decodes the next packet, feeds the encoder only its first 312 samples to drain the lookahead,
   puts that packet back in the demuxer, and forwards it unchanged. The samples fed twice are
   counted once in the media position.

On real FFmpeg files the first block after the seam measures between -18 and -33 dB relative to
the signal after a seek, and -25 dB after a promotion, which is the level of the encoder's own
re-encoding noise; blocks settle below -45 dB within eight packets.

### Gain and filter changes

A gain or filter change on a 312-pre-skip stream is seamless in both directions. Entering PCM, the
encoder is primed with the audio the client has already been sent (the rolling packet history,
decoded once for warm-up) so it starts converged instead of cold, and the first re-encoded frames
that would repeat audio the client already played are suppressed. Leaving PCM uses the same
junction as a seek. Tests insert gain changes at every offset around the return to packets and
check that no sample is repeated or dropped on either side. Streams with another pre-skip keep the
earlier behavior and its short artifact.

### Fallback seeking

When [fallback seeking](/docs/core/playback#fallback-seeking) swaps in a replacement decoder, a
stream that is being forwarded as packets keeps being forwarded unchanged while the replacement is
prepared. Once it is ready, the stream is converted to PCM with the seamless entry above, so the
encoder is primed with what the client just heard, then the decoders are swapped at one sample.

The stream then returns to packets, as after a seek, from the replacement's own packets. The one
extra requirement is alignment. The encoder's partial 20 ms frame and the replacement's packet grid
advance together, so they coincide at a packet boundary only when the replacement's first sample has
the encoder's phase. Its start is therefore moved forward by under 20 ms (the seek's position
already carries tens of milliseconds of preparation time) so that they do. The encoder then runs
for six frames, so the client's decoder has settled on the re-encoded audio, and the usual lookahead
junction hands over to source packets. This needs a stream whose pre-skip equals the encoder
lookahead (312), an Opus output, and a known encoder phase; any other stream stays on PCM, as it
does after an ordinary seek.

Measured on a 15-minute 128 kbit/s Opus track over a range-ignoring origin, the stream is back on
packets about 150 ms after the swap and costs the same CPU as before the seek (1.0% of a core), where
staying on the PCM path costs 3.7-3.9%. The timeline is contiguous across conversion, swap and
recovery, and the packets after it decode, in a fresh libopus decoder, to what FFmpeg decodes. The
crossfade worker does the same.

### Reported position and what the listener hears

For straight passthrough and for gain or filter changes, the reported media position is the media
time the client has been sent, which is what it plays (to within the 6.5 ms pre-roll). After a
**seek or promotion**, the re-encoded segment is accounted in the input domain: the reported
position leads the audio the listener hears by the encoder's constant 312 samples (6.5 ms) until
the stream returns to packets, the same convention the PCM path has always had. Reported
durations, positions and synchronized-lyrics timestamps therefore stay within 6.5 ms of the
audible audio through seeks, crossfades and tempo changes; tests assert both bounds.

A seek decodes only the packet that contains the target (FFmpeg trims it to the exact sample),
then about six more packets, then forwards source packets again. A seek to a position that is not
a multiple of 960 samples starts the first output packet at the target; its leading silence is
shorter than one packet.
