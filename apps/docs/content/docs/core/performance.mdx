Use the repository benchmark to compare concurrent playback workloads without Discord credentials. Its controlled sinks measure processing and backpressure. They do not measure live RTP or Discord delivery.

## Native processing and memory

Each FFmpeg filtergraph uses one processing thread on its owning playback worker.
This prevents FFmpeg's automatic graph threading from creating a pool sized to
the machine for every session. Filters still run through native libavfilter.
Filter expressions, master volume, and Opus quality settings are unchanged.
Particularly expensive graphs should be measured with representative input.

The decoder reuses its exclusively owned native resampling output frame, growing
it when required. Returned PCM remains independently owned. Seeking and processing
mode changes release resampler state through the existing lifecycle.

The Opus adapter encodes into bounded scratch storage and transfers only an
allocation sized to the encoded payload to its sink. It still emits 20 ms stereo
packets and uses complexity **9**, bitrate **128000**, and VBR by default.
Configuration remains available through the existing audio Opus settings. Lower
complexity is an explicit application choice.

## Reproduce measurements

From the repository root, with the supported FFmpeg development libraries available:

```sh
cargo build --release -p remedia-core --example concurrent_playback_benchmark
python3 benchmarks/playback.py --output /tmp/remedia-playback.jsonl
```

On this development machine, Cargo needs
`PKG_CONFIG_PATH=/opt/homebrew/opt/ffmpeg/lib/pkgconfig` to select the supported
FFmpeg installation. Use your installation's pkg-config path on other hosts.

The runner uses checked-in generated Opus and MP3 fixtures, 1, 8, 32, 64, and 128
sessions, three repetitions, and separate paced and unpaced runs. Workloads select
automatic passthrough, volume processing, or a native tremolo graph. MP3 always
transcodes, including in the automatic workload. No external service or Discord
credentials are used. Override counts and repetitions with `--counts 1,32,128`
and `--repeats 3`. `--binary PATH` selects a previously built executable.

For a longer local fixture or a different encoder complexity, invoke the example:

```sh
target/release/examples/concurrent_playback_benchmark ./long-track.aac 128 filter paced 9
```

The JSON output includes wall time, delivered audio seconds, packet count,
cumulative packet allocation capacity, startup p99, and sink deadline delay p95
and p99. The runner adds child process CPU seconds and samples RSS and thread count
approximately every 20 ms on macOS and Linux. Short unpaced runs can finish between
samples, so their resource peaks are lower bounds. Startup is measured per session.
Sessions start sequentially. Deadline delay is relative to each sink's first packet.
Percentiles use the sorted observation at `floor((n - 1) * percentile / 100)`.

The paced sink directly backpressures delivery at audio deadlines, retaining no
packet queue. Its delay is **not measured Discord RTP delay**. Cumulative packet
capacity is neither live memory nor a process-wide allocation profile. CPU time
includes source opening and teardown, without attributing time to individual audio
stages. The short fixtures are regression probes, not sustained load qualification.
The repository's `benchmarks/` report records the measured environment and results.

## Crossfade curves

The mixer cost of `adaptive` against `equalPower` was measured with
`cargo run --release -p remedia-core --example crossfade_adaptive -- bench`. The example mixes 5 s of
48 kHz stereo in 960-frame blocks, counts heap allocations with a counting global allocator, and takes the
median of nine repeats on an Apple M5 (single thread, Rust 1.99.1).

| Case                                      | ns per frame | One stream, real time | Allocations |
| ----------------------------------------- | -----------: | --------------------: | ----------: |
| `equalPower`, limiter idle                |          2.8 |               0.013 % |           0 |
| `adaptive`, limiter idle                  |          3.6 |               0.017 % |           0 |
| `equalPower`, loud masters (limiter busy) |          3.1 |               0.015 % |           0 |
| `adaptive`, loud masters (limiter busy)   |          3.8 |               0.018 % |           0 |

Adaptive adds about 0.7 ns per frame (roughly 25%), which is under 0.005% of one core for a stream.
Neither curve allocates while mixing, and the adaptive state is a fixed-size struct inside the crossfade.
These figures cover the mixer only, not decoding, Opus encoding, or the playback worker.

`-- render <directory>` writes a 16-bit stereo WAV per scenario and curve, plus a loudness summary, from
deterministic synthetic programme material, so the same audio can be regenerated and auditioned on any
machine. The checked-in [report](https://github.com/twlite/remedia/blob/main/benchmarks/adaptive-crossfade.md)
lists the metrics. The metrics compare the output with a smoothstep glide between the two tracks' own levels;
they check that the controller does what it is designed to do and are not a listening test.

## Remaining architecture limits

A shared CPU scheduler has not replaced playback workers. Moving the current loop
into a fixed pool would allow synchronous network reads, staging joins, or output
backpressure to occupy every worker. A scheduler change requires separate bounded
I/O and output handoffs, decoder ownership, readiness notification, and comparison
against the paced baseline before adoption.

Crossfade-enabled direct sources use eligible Opus passthrough outside overlaps.
A promoted eligible Opus source hands its decoder to the playback worker after the
overlap and resumes packets; other promoted sources keep PCM ownership and continue
transcoding. A seek also returns an eligible Opus source to packets after the one packet
that contains the target. Ordinary
sessions retain adaptive Opus passthrough and live processing transitions described
in [Playback sessions](/docs/core/playback). Direct-source transitions use bounded codec preroll and exact packet boundary
accounting.

Encoder state remains serialized with packet submission to preserve ordering and
seek barriers. Staging cancellation still joins its worker before exposing terminal
completion. Long-running crossfades, AAC, stalled HTTP sources, command latency,
per-stage CPU/I/O attribution, queue occupancy, and live RTP/DAVE reliability need
additional performance workloads beyond this benchmark.

## Opus pre-skip, packet recovery, and release builds

The measured effect of forwarding real FFmpeg/libopus Opus files (pre-skip 312), recovering
packets after seeks and crossfade promotions, the packet-path allocation changes, memory owners of a
staged session, link-time optimization, and the optimizations that were measured and rejected are in
[`benchmarks/phase3.md`](https://github.com/twlite/remedia/blob/main/benchmarks/phase3.md), with the exact
commands in [`benchmarks/README.md`](https://github.com/twlite/remedia/blob/main/benchmarks/README.md).
Headline numbers at 512 paced sessions on one Apple M5 host: real Opus playback used 86% less CPU and
48% less peak RSS; the same with a seek every 3 s used 64% less CPU; and two crossfade promotions per
session used 55% less CPU, 27% less RSS, and 25% fewer threads. Sources that cannot be forwarded
(MP3, AAC, filtered or gain-adjusted Opus) are unchanged.

Release builds use fat link-time optimization. Measured, it changes run time by only about 1-2%,
inside the noise, because most CPU is spent in libopus and FFmpeg, which are outside Rust's LTO.
Its effect is on the binary: the server runtime is 13.4 MB instead of 21.4 MB (thin LTO: 18.8 MB),
for a clean release build that takes 79 s instead of 33 s (thin: 45 s).

## Fallback seeking

[Fallback seeking](/docs/core/playback#fallback-seeking) serves a seek on a source that cannot seek by
opening a second decoder on the same track while the first keeps playing. Measured on one Apple M5
host against a loopback HTTP origin that ignores `Range`, with a 15-minute Opus track and a
15-minute MP3 track and a real-time paced output (exploratory, one run per row):

- No underruns in any row, and the longest interval between frames reaching the output was the
  frame duration (20 ms Opus, 25 ms MP3). The preparation does not touch the playback worker.
- A fast origin takes about 30 ms to swap, and 50 ms for a seek to 13 minutes. At 100 Mbit/s the
  seek takes the time to transfer the track up to the target: 290 ms for 5 minutes of Opus, 711 ms
  for 13 minutes, 1.5 s for 13 minutes of MP3. Extra work is one connection and one decoder.
- CPU is 4-93 ms per seek. Compressed packets that end more than a second before the target are
  dropped without being decoded.
- Without the option the same Opus seeks all failed after 4-7 reconnects and 29-36 MB of transfer for
  a 9.8 MB file, and no audio reached the output in the following 300 ms. An MP3 seek succeeded by reading the skipped bytes on
  the playback worker.

Commands, tables and caveats are in
[`benchmarks/fallback-seeking.md`](https://github.com/twlite/remedia/blob/main/benchmarks/fallback-seeking.md).
