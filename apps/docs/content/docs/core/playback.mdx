A Rust `PlaybackSession` owns a source, an output, and a blocking playback worker. Use it to coordinate decoding, pause/resume, seeking, and cleanup. [Output adapters](/docs/core/outputs) consume its PCM or Opus packets.

Node.js integrations should start with the [binding reference](/docs/node/bindings). Contributor measurements and worker limits are in [Performance](/docs/core/performance).

## Start and observe playback

Choose an explicit file or HTTP(S) source and move an output into the session.
`play()` blocks until FFmpeg has opened the input and initialized the audio
decoder. It returns the selected stream metadata only after that succeeds.
Decoding and frame delivery then run on the session worker.

`play_with_cancellation(source, output, token)` accepts a caller-owned
`CancellationToken`. A token cancelled before the worker starts prevents the
source from opening. After startup it interrupts decoder I/O. Call `stop()` as
well to join the worker and release its output. Ordinary callers can use
`play()`, which creates its own token and is cancelled by `stop()`.

Async code can await `token.cancelled_async()` instead of waking on a periodic timer.
The future returns immediately when the token is already cancelled; dropping a pending
future unregisters its waiter without keeping the task alive. The same token still
interrupts synchronous decoder I/O through `cancel()`.

```rust
use remedia_core::{InputSource, NullOutput, PlaybackSession, PlaybackState};

let session = PlaybackSession::new();
let output = NullOutput::new();
let stats = output.stats_handle();
let info = session.play(InputSource::file("media/track.wav"), output)?;

println!("{}; duration: {:?}", info.codec, session.duration());
println!("state: {}", session.state());
let terminal_state = session.wait();
assert_eq!(terminal_state, PlaybackState::Completed);

let position = session.position();
println!("media: {:?}; submitted: {:?}; consumed: {:?}", position.media, position.submitted, position.played);
println!("output statistics: {:?}", stats.snapshot());
session.stop()?; // joins and releases the finished worker/output
# Ok::<(), Box<dyn std::error::Error>>(())
```

The null output consumes frames as fast as decoding permits. It is useful for
tests, examples, and benchmarks. It does not pace playback in real time. See
`crates/remedia-core/examples/playback.rs` for a runnable example that uses an
example-only paced null output so pause and seek are observable with short files.

## States and operations

| State       | Meaning                                                                 |
| ----------- | ----------------------------------------------------------------------- |
| `Idle`      | No source has been started.                                             |
| `Starting`  | The worker is opening the source and decoder.                           |
| `Playing`   | The worker may decode and deliver frames.                               |
| `Pausing`   | Pause was requested and is waiting for the current operation to finish. |
| `Resuming`  | The output is resuming before frame delivery continues.                 |
| `Paused`    | The worker waits on a condition variable and does not decode ahead.     |
| `Stopping`  | Cancellation is in progress and the worker is being joined.             |
| `Stopped`   | Active work was cancelled and its worker joined.                        |
| `Completed` | Natural end-of-stream and output finish both succeeded.                 |
| `Failed`    | A decoder, output, or worker error stopped playback.                    |

`pause()` waits until the worker reaches a frame boundary. It can wait for the
current native input read or output write to return. `resume()` wakes the worker.
Repeating pause while paused or resume while playing is harmless. `stop()` cancels
network reads and output work, clears pending seek requests, and joins the worker.
Stopping an idle session changes it to `Stopped`. Stopping a completed or failed
session releases retained output resources while preserving its terminal state.

A session holds only one active source. A second `play()` call while it is
starting, playing, pausing, paused, or stopping returns
`PlaybackError::InvalidState`. To replace a source, call `stop()` and then
`play()` with the new source and a new output value. Applications own playlists. Opted-in sessions can promote a staged next source through [crossfade playback](/docs/core/crossfade).

`PlaybackSession::wait()` blocks the calling thread until the current source
reaches a terminal state. For async code, capture a
`PlaybackSession::completion()` waiter and await `PlaybackWaiter::wait_async()`:

```rust
use remedia_core::{PlaybackSession, PlaybackState};

async fn wait_for_track(session: &PlaybackSession) -> PlaybackState {
    let waiter = session.completion();
    waiter.wait_async().await
}
```

The future uses Rust's standard `Future` interface, does not require a particular
async runtime, and does not block a worker thread. It returns the same
generation-specific state as `PlaybackWaiter::wait()`, including `Stopped` if a
replacement starts before the waiter observes completion. Dropping a pending
future deregisters its waker. Adapters that cross an async scheduling boundary
can capture `completion_generation()` synchronously and later create the
corresponding waiter with `completion_for_generation(generation)`, so an old
completion cannot attach to a new track.

## Seeking and position

`seek(Duration)` is supported while playing or paused. For files, buffers, and
seekable HTTP inputs, the decoder asks FFmpeg's demuxer to seek, flushes
codec/resampler state, and discards samples before the target. The session flushes
pre-seek output before resuming delivery. HTTP seeking depends on the server
and container, and a known source duration is checked before the request.

For one-shot `InputSource::byte_stream`, seeking is **forward only**. The decoder
reads and discards audio up to the requested media timestamp, retaining only
its bounded input queue and decoder buffers. It never rewinds the producer or
estimates byte offsets from bitrate. Large jumps require consuming the intervening
encoded data and can take time or incur CPU/network work. Backward requests
return `PlaybackError::UnsupportedSeeking` without flushing output or stopping
the session. The earliest decodable sample can be slightly ahead of the last
submitted position because FFmpeg and the playback worker read ahead. A seek
past EOF returns `SeekOutOfRange`. A stalled producer keeps the seek waiting
until data arrives or the operation is cancelled.

The same holds for an HTTP origin that ignores `Range` requests. FFmpeg reports its I/O as
non-seekable, and Remedia then never hands it to FFmpeg's seek: that attempt reconnects repeatedly
(in measurements, 4-7 times and three times the file's size in transfer for a seek into a 15-minute
Opus track) and can leave the read position lost, so no audio follows. A forward target walks the
decoded stream in place, like a byte stream; a rewind is refused with `UnsupportedSeeking` before
anything is touched. A seek that fails for any reason leaves the stream as it was, including
forwarded Opus packets: the demuxer is asked first and nothing else is changed until it agrees.

A source that cannot seek at all can be served by a replacement instead; see
[Fallback seeking](#fallback-seeking).

## Fallback seeking

Some sources cannot reposition their decoder: an HTTP origin that ignores `Range` requests, a format
without a usable index, or a one-shot stream whose producer can issue a new one. Without the option, a
rewind on such a source is refused and a forward seek walks the stream on the playback worker (see
[Seeking and position](#seeking-and-position)). With fallback seeking enabled, the session leaves the
active decoder alone and prepares a replacement instead.

```rust
session.configure_fallback_seeking(true); // off by default; may be changed at any time
session.seek(Duration::from_secs(90))?;   // returns when the replacement is audible

let outcome = session.seek_outcome(Duration::from_secs(90))?;
// outcome.requested == 90 s; outcome.applied is where the audio continues from, for example 93 s
```

The mechanism:

1. The worker keeps playing the current source. A short-lived `remedia-fallback-seek` thread opens
   the same track again (see [what can be reopened](#what-can-be-reopened)), skips compressed packets
   that end more than a second before the target without decoding them, then decodes and discards
   forward.
2. The thread follows the **effective playhead**. The seek asks for 90 s; if three seconds of the
   current source play while the replacement is prepared, the replacement parks on about 93 s.
   The offset is the amount the _source timeline_ advanced, not wall-clock time: it stops while
   the session is paused and runs faster than real time under a tempo filter (`atempo=1.5` for
   three seconds of output is 4.5 s of source), so the audio resumes where the listener would be.
3. When the replacement is parked the worker swaps the decoders at one exact sample. Opus
   passthrough is left first (see below). The first 5 ms of the new audio are blended in with an
   equal-power fade against the audio it replaces, which is enough to prevent a click and too short
   to hear as a crossfade. No audio is repeated, and nothing is flushed: audio already queued in the
   output plays out, so the output timeline stays contiguous.
4. `seek()` returns `Ok(())` at the swap. The source position jumps once, from the old source's
   position to the replacement's; it never moves backwards because of preparation latency. The
   stream metadata and duration are refreshed from the replacement.

### Where the seek landed

`seek_outcome()` and `PendingSeek::wait_outcome()` return a `SeekOutcome { requested, applied,
replaced_source }`. For an ordinary seek `applied == requested`. For a fallback seek `applied` is the
requested position plus the source time that elapsed during preparation, and `replaced_source` is
set. The output timeline did not restart then (`submitted` position keeps counting), so a caller that
keeps its own clock moves its _media_ position to `applied` and leaves elapsed output time alone.
`position().media` and the crossfade `TimelineChanged` event (`position_ms`, `requested_position_ms`,
`replaced_source`) report the same position, in a crossfade session as well.

### Cancelling a seek

A seek has a ticket that the worker commits immediately before it changes anything audible.
`PendingSeek::canceller()` returns a `SeekCanceller`, and `PlaybackSession::cancel_seek()` cancels
the latest seek:

```rust
let pending = session.start_seek(position)?;
let canceller = pending.canceller();
// ... the request that asked for this seek times out ...
if canceller.cancel() {
    // guaranteed: the seek will never be applied; pending.wait() fails with SeekCancelled
} else {
    // too late: it was already being applied, and pending.wait() reports its outcome
}
```

The answer is exact, not best effort: a cancel that wins the race means the seek can no longer
happen, and one that loses says so. A queued seek and a preparing replacement can both be cancelled;
an ordinary in-place seek is applied the moment the worker reaches it, so there is little to cancel.
The playing source is never interrupted by a cancel.

Anything that goes wrong leaves the original stream playing normally:

| Situation                                                         | Result                                                                           |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------- |
| The track cannot be reopened (HTTP error, expired grant, refused) | `seek()` fails with the open error; playback continues                           |
| The target is past the end of the replacement                     | `SeekOutOfRange`; playback continues                                             |
| The replacement does not catch up within 60 s                     | `UnsupportedSeeking`; a source slower than real time can never catch up          |
| A newer `seek` is submitted                                       | The older call fails with `SeekSuperseded`; only the latest seek can replace     |
| A crossfade overlap begins first                                  | `SeekSuperseded`; the track is ending and the transition goes ahead              |
| `stop()`, a new `play`, a failure, or dropping the session        | The preparation is cancelled and joined; the waiting call fails with `Cancelled` |
| The old source ends before the replacement is ready               | The worker waits for the replacement rather than completing the playback         |

At most one preparation exists per session. It owns one extra decoder, one extra connection and
a thread, all released on every path above; staging is not involved, so memory stays bounded.

### What can be reopened

A reopened source must still be the track that is playing. Before it is used, its codec, sample
rate and channel count must equal the playing stream's, and so must its duration (to within one
second or one percent) when both are known; a plugin that answers differently the second time, or a
URL whose content was replaced, fails the seek instead of dropping the listener into another
recording. A duration only one of them can determine proves nothing, so a one-shot stream whose
length was unknown can be reopened as a complete file.

| Source              | Fallback seeking                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------ |
| `File`, `Bytes`     | Not needed: the demuxer seeks. If a demuxer still reports it cannot, the file is reopened. |
| `HttpUrl`           | Reopened from the same URL, with the same options and the same network restrictions.       |
| `SequentialHttpUrl` | Never: it is typically a single-use grant. Fails with `UnsupportedSeeking`.                |
| `ByteStream`        | Only with a [`SourceReopener`](#source-reopeners). Otherwise `UnsupportedSeeking`.         |

A decoder is only asked to seek in place when it can: Remedia checks whether the FFmpeg I/O
context is seekable before touching it. Reopening the same `HttpUrl` sends exactly the request the
first open sent. It cannot carry anything the original request did not, and a URL that has since
expired fails like any other reopen.

### Source reopeners

A source Remedia cannot reopen by itself, such as a stream produced from a single-use grant,
supplies a `SourceReopener`:

```rust
use std::sync::Arc;
use remedia_core::{CancellationToken, InputSource, ReopenError, SourceReopener};

struct Grant { /* whatever issues a new stream */ }

impl SourceReopener for Grant {
    fn reopen(&self, cancellation: &CancellationToken) -> Result<InputSource, ReopenError> {
        // Called on a background thread, never on the playback worker. Return promptly once
        // `cancellation` is cancelled. The input must play the same media from its first sample.
        self.issue_stream(cancellation).map_err(|error| ReopenError::new(error.to_string()))
    }
}

session.play_with_reopener(source, Arc::new(Grant { /* ... */ }), output, CancellationToken::new())?;
session.stage_next_with_reopener(next, Arc::new(Grant { /* ... */ }), identity, None)?;
```

Do not put credentials or signed URLs in a `ReopenError` message: it reaches the caller of `seek()`.
A staged source keeps its reopener, so a track that was promoted by a crossfade can still be sought.

### Submitting without waiting

`seek()` blocks until the swap. A caller that serializes playback operations behind a lock, as the
server does, uses `start_seek()` to submit under the lock and wait without it:

```rust
let pending = session.start_seek(position)?; // validates and submits
// release the lock here; a newer seek, pause or stop can now reach the session
pending.wait()?;                              // PendingSeek::wait
```

### Interaction with other features

- **Opus passthrough.** Swapping decoders blends decoded audio, so forwarded packets are left
  first using the seamless entry described in [Opus passthrough](/docs/core/opus#gain-and-filter-changes).
  Packets keep flowing unchanged while the replacement is _preparing_; the conversion happens only
  once it is ready. After the swap the stream returns to the replacement's own packets through the
  usual recovery, see [Opus: fallback seeking](/docs/core/opus#fallback-seeking). `processing_mode()`
  reports `Transcoding` meanwhile (about 150 ms in the benchmark) and `Passthrough` again afterwards.
- **Crossfade.** The swap publishes a `TimelineChanged` event, advances the source generation and
  invalidates the staged next track, exactly as an ordinary seek does. A transition that starts
  before the replacement is ready supersedes the seek.
- **Filters and gain.** The filtergraph is kept, not rebuilt. It holds a little audio of the old
  source (a tempo filter about a hundred milliseconds), which plays out across the swap.
- **Diagnostics.** `core.playback.fallback_seek_started`, `_applied` (with target, applied position,
  compensation and preparation time), `_failed` and `_timed_out`.

## Structured diagnostics

`PlaybackSession::with_observability(handle)` attaches a session to the shared local tracing
dispatcher and metrics provider. Each playback start receives its own internal `playback_id`. Events
include lifecycle transitions and failures without recording source paths or URLs. See the
[observability guide](/docs/observability/configuration) for subscriber ownership, event routing,
environment configuration, and OTLP export.

## Errors

Startup errors are returned from `play()`. Errors after startup set the state to
`Failed` and remain available from `last_error()`. `PlaybackError` distinguishes
decoder failures, output failures, invalid state operations, worker startup or
panic, cancellation, seek range errors, unsupported seeking, and a seek that a newer one
superseded (`SeekSuperseded`). The original
decoder or output error remains available as the error source where possible.

## Runnable example

From the repository root, run:

```sh
cargo run -p remedia-core --example playback -- file ./media/track.wav
cargo run -p remedia-core --example playback -- url https://example.com/audio.mp3
```

The example prints metadata, state, submitted/played position, and null-output
statistics. It requests pause, attempts a midpoint seek, resumes, observes
completion, and stops the session. It reports unsupported seeking for sources
that cannot seek.

## Experimental shared executor

The non-default Cargo feature `experimental-scheduler` is propagated through core, Discord,
Node and server crates. Enabling it preserves dedicated execution for existing constructors.
Rust embedders can explicitly share a fixed pool:

```rust
use remedia_core::{InputSource, NullOutput, PlaybackScheduler, PlaybackSession};

let scheduler = PlaybackScheduler::new(2, 1024)?;
let session = PlaybackSession::with_scheduler(scheduler.clone());
session.play(InputSource::bytes(encoded_media), NullOutput::new())?;
// Stop joins both startup and scheduled processing before releasing output ownership.
session.stop()?;
```

This experiment schedules owned-byte and local-file Ogg, MP3, ADTS AAC, WAV and FLAC inputs with
`NullOutput`, `StreamOutput` with unpaced or realtime pacing, or `OpusEncoderOutput` attached
to `DiscordOpusSender` / `RoutedOpusSender`, including CPU-only native filtergraphs.
Full streaming queues suspend production using the existing readiness waker; consumption through
`StreamReader::poll_next` wakes production. Buffer limits, encoding settings and EOF are unchanged.
Network sources, other containers (including MP4/M4A), producer byte streams,
synchronous custom outputs and crossfade retain dedicated execution. Eligible sources open and probe on a bounded shared two-thread startup executor. A full
startup queue returns a worker-initialization error instead of creating additional threads.
Unsupported source/output combinations retain dedicated startup and playback. A seek or live filter update transfers exclusive ownership of the same machine to a shared,
bounded two-thread control executor for one operation. It then returns to CPU scheduling.
No permanent control thread is added per session. A stalled control can delay other controls,
but cannot occupy a codec worker; cancellation continues to interrupt its existing source and
output waits. Codec
actions still do not have a hard CPU-time budget. The pool is therefore experimental and is not a replacement for production scheduling.

`executor_diagnostic()` identifies scheduled execution or dedicated fallback for an unsupported
workload, full pool, or a control requiring dedicated execution. `scheduler.diagnostics()` reports worker count, admitted sessions, queue
depth and action count. Capacity bounds admitted scheduled sessions; excess sessions fall back to
dedicated execution, so it does not cap total engine concurrency. Pool creation rejects zero counts
and returns thread creation failures. Existing Node and RPC playback APIs remain dedicated; this
branch does not add a JavaScript or remote executor-selection API.

For budget experiments, `PlaybackScheduler::with_processing_budget(workers, capacity, actions_per_turn)`
sets a positive maximum action count per queue dispatch. `new` keeps its existing one-action budget.
Every action checks controls and readiness; the budget does not bound native codec wall time.
Larger bursts reduce queue dispatches but can increase the time before another session runs.

Diagnostics distinguish cumulative `admitted` from currently `scheduled_sessions`; `sessions`
also includes admitted jobs temporarily awaiting isolated controls. `control_workers`,
`queued_controls`, `isolated_controls` and cumulative `control_handoffs` identify this work;
`control_fallbacks` counts only dedicated migrations for native graphs outside the CPU-only
whitelist; ordinary seek/filter handoffs return to scheduling. Dedicated fallbacks are counted
separately by capacity, control migration, input, output, demuxer, initial filtergraph and crossfade.
`turns`, `actions`, `queue_peak`, `queue_contentions` and `queue_wait_ns` expose dispatch frequency
and queue mutex waiting. Contention counts failed immediate mutex acquisitions; wait time includes
OS descheduling while waiting, and is not isolated mutex instruction cost. These counters do not
change production executor selection or qualify fallback workloads as scheduler performance.

Realtime streams now use `scheduler_poll_deadline`: a future absolute `Instant` suspends the job
in the pool's ordered deadline queue. Workers sleep on the readiness condition variable until
work or the next deadline arrives. No timer thread is created per session. Each job has at most
one deadline; control, output and cancellation wakes remove it before enqueueing the job, so
stale timers cannot run a later playback generation. Paused streams stop scheduling deadlines.
`pending_deadlines`, `deadline_peak`, `deadline_suspensions` and `deadline_wakes` expose this state.

Custom outputs keep their existing defaults. The new optional method delegates to
`scheduler_poll_ready` unless overridden. An output opting in must expose capacity without
blocking and retain no more queued audio than its existing buffering contract permits. Returning
a pacing deadline must not consume the next frame. Scheduling deadlines is not a hard realtime
or Discord RTP delivery guarantee; overloaded codec work can still deliver audio late.

Capacity and pacing use separate producer wake registrations. Draining a chunk wakes a producer
waiting for queue space; it does not wake a producer whose only wait is a future pacing deadline.
Closing, failing, flushing or explicitly waking the output still interrupts a pacing wait. This
keeps downstream backpressure responsive without repeatedly removing and rearming the same timer.

Pool sizing must cover short codec-work bursts as well as average CPU. High-concurrency local
measurements found worse tail-delivery gaps with small pools during the Opus transition needed
for container trimming. The experimental pool does not bound concurrent startup threads, and
`for_available_parallelism` still caps its convenience policy at four workers. These limitations
remain under evaluation; existing dedicated playback stays the production default.

Sizing also needs to account for initialization: each source still opens and probes on its own
startup thread before pool admission. Concurrent stalled probes can therefore create many startup
threads, even when a small CPU worker count is configured. The CPU admission cap does not bound
that opening phase; unsupported inputs subsequently remain dedicated.

The experimental Discord output uses the same bounded transport queues and RTP actor as dedicated
playback. A full packet queue suspends codec production; draining it wakes the session. Packet
ownership stays with the output until admission succeeds, including while a router is detached.
PCM is retained as one owned input frame and encoded in 20 ms slices, with at most two pending
encoded packets (EOF can flush two). Pause, resume and finish use resumable acknowledgements;
completion is published only after the actor acknowledges the finish barrier. RTP deadlines,
sequence numbers, timestamps, DAVE and transport encryption remain owned by the transport actor.
No codec worker waits for a socket, transport replacement or acknowledgement. This capability is
opt-in on `OpusPacketSink`; existing custom sinks keep their synchronous contract and dedicated
execution. Compile both core and Discord with `experimental-scheduler` when using it.

Custom readiness-aware outputs can override `scheduler_activate` (called once after admission)
and `scheduler_poll_control(control, cx, cancellation)`. A pending control must retain its
operation, register the waker and acknowledge it exactly once before returning success. Legacy
outputs use the existing synchronous pause/resume/finish defaults.

Local files demux on a separate shared two-thread executor. A read-ahead burst transfers up to
eight owned FFmpeg AVPackets through a readiness-driven queue, targeting at most 128 KiB; one
larger source packet is retained whole, as on the direct decoder path. Codecs, resampling and
filters stay on CPU workers. Empty compressed queues suspend the session, and a completed burst
wakes it. Seeking waits for its in-flight burst on the isolated control executor, then discards
old read-ahead after the native seek succeeds. Cancellation and `stop` join outstanding reads.
The file is read incrementally and is never copied wholesale into memory for eligibility.
`io_workers`, `queued_io`, `active_io`, `io_queue_peak`, `io_bursts` and `io_busy_ns` identify
this executor. These are fixed pools, not additional permanent threads per session.

`for_available_parallelism()` now uses the platform's available CPU count and an eight-action
budget, with 1024 admission slots. Explicit `new(workers, capacity)` still uses one action;
`with_processing_budget` retains caller-selected fixed values. No dynamic resizing is enabled.
HTTP and producer/plugin streams remain dedicated: a stalled native read could otherwise
occupy every bounded I/O worker and delay unrelated sources. This branch does not claim those
fallbacks as scheduled performance, and scheduled crossfade remains deferred.

Discord controls and in-flight pause/finish barriers are fenced by output generation. A seek
while finish acknowledgement is pending invalidates the old barrier and resumes the same
playback machine; the old acknowledgement cannot complete the new timeline. Local read-ahead
completion wakes a session only when it is waiting for input, preserving output pacing deadlines.

The current CPU-only filter whitelist is `anull`, `aformat`, `aresample`, `volume`, `atempo`,
`bass`, `treble`, `equalizer`, `highpass`, `lowpass`, `bandpass`, `bandreject`, `pan`, `asetrate`
and `asetpts`, plus the engine's `abuffer`/`abuffersink` endpoints. Classification inspects the
configured native graph, including automatically inserted adapters. Other filters can perform
I/O or invoke external plugins despite having one audio input/output; they retain dedicated
execution. A live replacement with such a graph drains retained production on a tracked dedicated
fallback, then continues there for that generation. Its fallback is explicit in diagnostics and
is excluded from scheduler performance claims. Normal CPU-only replacements remain reversible.
Pause can supersede a pending EOF acknowledgement; resume requests a fresh finish barrier without
encoding or replaying the tail again.

Scheduled seeking isolates native decoder/filter repositioning, then retains the seek request
while `scheduler_poll_flush_samples(sample, cx, cancellation)` waits for output invalidation.
Its acknowledgement is published only after the flush and encoder alignment succeed. Discord
flush admission and acknowledgement use the same asynchronous control path as other barriers;
a detached transport parks the seek without occupying either a codec or isolated control worker.
Later controls remain ordered behind that seek, and stop cancels and acknowledges outstanding
requests before joining. Custom scheduling outputs whose flush can wait must override this poll;
the default calls `flush_samples` for outputs with an already nonblocking flush.

Bounded startup pins FFmpeg's `format_whitelist` before container headers and stream probing,
so containers outside the supported set cannot open nested inputs on a shared startup worker.
A rejected/failed restricted probe retries the original source on a tracked dedicated worker;
`probe_retries` reports these attempts. Unsupported containers keep their original playback
functionality, and these retries/fallbacks are excluded from scheduler benchmark evidence.

MP3, MP2 and AAC native seeks decode up to one second before the requested position to
restore codec history, then discard preroll samples. Scheduled sessions reposition
the demuxer on the isolated control executor and decode preroll in bounded codec
turns. The seek acknowledgement still waits for output invalidation; recovery before
the first post-seek audio can take longer without changing the requested media
position or encoder quality.
