title: Playback sessions
description: Manage playback state, output delivery, position, and worker cleanup.
---

`PlaybackSession` manages one source and one output instance. It uses a dedicated
blocking worker for that session, while `AudioDecoder` remains unpaced and
pull-based. The core also provides a transport-independent Opus output adapter;
the [Discord voice guide](/docs/discord/voice-output) shows how to connect it to the Discord
transport.

See [Playback performance](/docs/core/performance) for concurrent benchmark commands,
filter worker limits, and measurement boundaries.

## Start and observe playback

Choose an explicit file or HTTP(S) source and move an output into the session.
`play()` blocks until FFmpeg has opened the input and initialized the audio
decoder; it returns the selected stream metadata only after that succeeds.
Decoding and frame delivery then run on the session worker.

`play_with_cancellation(source, output, token)` accepts a caller-owned
`CancellationToken`. A token cancelled before the worker starts prevents the
source from opening; after startup it interrupts decoder I/O. Call `stop()` as
well to join the worker and release its output. Ordinary callers can use
`play()`, which creates its own token and is cancelled by `stop()`.

```rust
use remedia_core::{InputSource, NullOutput, PlaybackSession, PlaybackState};

let session = PlaybackSession::new();
let output = NullOutput::new();
let stats = output.stats_handle();
let info = session.play(InputSource::file("media/track.wav"), output)?;

println!("{}; duration: {:?}", info.codec, session.duration());
println!("state: {}", session.state());
let terminal_state = session.wait();
assert_eq!(terminal_state, PlaybackState::Completed);

let position = session.position();
println!("media: {:?}; submitted: {:?}; consumed: {:?}", position.media, position.submitted, position.played);
println!("output statistics: {:?}", stats.snapshot());
session.stop()?; // joins and releases the finished worker/output
# Ok::<(), Box<dyn std::error::Error>>(())
```

The null output consumes frames as fast as decoding permits. It is useful for
tests, examples, and benchmarks; it does not pace playback in real time. See
`crates/remedia-core/examples/playback.rs` for a runnable example that uses an
example-only paced null output so pause and seek are observable with short files.

## States and operations

| State       | Meaning                                                                 |
| ----------- | ----------------------------------------------------------------------- |
| `Idle`      | No source has been started.                                             |
| `Starting`  | The worker is opening the source and decoder.                           |
| `Playing`   | The worker may decode and deliver frames.                               |
| `Pausing`   | Pause was requested and is waiting for the current operation to finish. |
| `Resuming`  | The output is resuming before frame delivery continues.                 |
| `Paused`    | The worker waits on a condition variable and does not decode ahead.     |
| `Stopping`  | Cancellation is in progress and the worker is being joined.             |
| `Stopped`   | Active work was cancelled and its worker joined.                        |
| `Completed` | Natural end-of-stream and output finish both succeeded.                 |
| `Failed`    | A decoder, output, or worker error stopped playback.                    |

`pause()` waits until the worker reaches a frame boundary. It can wait for the
current native input read or output write to return. `resume()` wakes the worker;
repeating pause while paused or resume while playing is harmless. `stop()` cancels
network reads and output work, clears pending seek requests, and joins the worker.
Stopping an idle session changes it to `Stopped`. Stopping a completed or failed
session releases retained output resources while preserving its terminal state.

A session holds only one active source. A second `play()` call while it is
starting, playing, pausing, paused, or stopping returns
`PlaybackError::InvalidState`. To replace a source, call `stop()` and then
`play()` with the new source and a new output value. There are no playlists or
automatic next-source transitions.

`PlaybackSession::wait()` blocks the calling thread until the current source
reaches a terminal state. Async adapters should capture
`PlaybackSession::completion()` before dispatching that wait to a blocking
worker; its `PlaybackWaiter::wait()` remains bound to that source and returns
`Stopped` if a replacement starts first. Adapters that cross an async scheduling
boundary can capture `completion_generation()` synchronously and later create
the corresponding waiter with `completion_for_generation(generation)`. The
Node wrapper does this internally so an old completion cannot attach to a new
track.

## Seeking and position

`seek(Duration)` is supported while playing or paused. For files, buffers, and
seekable HTTP inputs, the decoder asks FFmpeg's demuxer to seek, flushes
codec/resampler state, and discards samples before the target. The session flushes
pre-seek output before resuming delivery. HTTP seeking depends on the server
and container, and a known source duration is checked before the request.

For one-shot `InputSource::byte_stream`, seeking is **forward only**. The decoder
reads and discards audio up to the requested media timestamp, retaining only
its bounded input queue and decoder buffers. It never rewinds the producer or
estimates byte offsets from bitrate. Large jumps require consuming the intervening
encoded data and can take time or incur CPU/network work. Backward requests
return `PlaybackError::UnsupportedSeeking` without flushing output or stopping
the session. The earliest decodable sample can be slightly ahead of the last
submitted position because FFmpeg and the playback worker read ahead. A seek
past EOF returns `SeekOutOfRange`; a stalled producer keeps the seek waiting
until data arrives or the operation is cancelled.

## Native FFmpeg filtergraphs and master volume

`PlaybackSession::set_filter_graph` accepts a trusted, raw libavfilter audio graph
expression with one effective audio input and output. The graph receives and
returns Remedia's packed stereo `f32`, 48 kHz PCM. FFmpeg validates filter names,
options, connections, and negotiated output format. Whitespace-only input is
rejected with `FilterGraphError::Empty`; pass `None` to clear filtering.

```rust
session.set_filter_graph(Some("bass=gain=8,treble=gain=-2"))?;
session.set_volume(0.75)?; // 75% linear master gain, independent of graph filters
println!("graph={:?}, gain={}", session.filter_graph(), session.volume());
session.set_filter_graph(Some("tremolo=f=5:d=0.6"))?; // replace while active
session.set_filter_graph(None)?;
# Ok::<(), Box<dyn std::error::Error>>(())
```

Remedia builds and validates a replacement graph before requesting a change.
The worker installs it at a decoded PCM boundary and discards delayed output
still held inside the previous graph. PCM already accepted by the output stays
accepted. A live change does not call the seek-flush operation, reset the Opus
encoder, invalidate queued RTP packets, reopen the source, or restart the
decoder. The Opus adapter keeps its partial frame, so one encoded packet can
contain accepted samples from either side of the graph boundary; sample
positions remain contiguous. Invalid replacements leave the current graph
active. Changes can be made before playback, while playing, or while paused;
pause and seek serialize with graph replacement. Stateful filter delay does not
carry across replacement. Seeking is different: it rebuilds filter state at the
new source position and flushes pre-seek output. Natural EOF drains delayed
output from the active graph before output completion.
If EOF wins a race with a queued graph update after no PCM boundary remains,
the update is acknowledged as the session's configuration for its next source;
it does not alter audio already being finished. A seek that loses the same EOF
race returns an invalid-state error instead of waiting indefinitely.

Filtergraphs may change duration or sample count. `seek(Duration)` remains
relative to the original media timeline. `position().media` is the source
position associated with the latest filtered PCM accepted by the output;
`Timestamp` means it came from a valid decoded source timestamp, while
`Estimated` means timestamps were missing or the graph can buffer/change the
source-to-output mapping. It is a processing position, not a claim about what a
listener has heard. `position().submitted` is the end of the contiguous
filtered-output sample timeline and is the timeline used by Opus. `played` is
the output's own consumed/audible report when available. Discord currently
reports no audible position. The Opus/RTP transport timeline remains continuous
across graph changes; a seek deliberately invalidates pre-seek queued media but
keeps the connection's RTP sequence and timestamp state.

The optional master gain is a finite linear value in `0.0..=2.0`: zero mutes,
one is unity, and 1.5 is 150% amplitude. Values outside that range, NaN, and
infinity return `PlaybackError::InvalidVolume`. Gain is applied after filtering
at a frame boundary. Output samples are clamped to `[-1.0, 1.0]`; gains above
unity can therefore clip and do not provide limiting or loudness normalization.
Volume and graph configuration survive track replacement on the same session
and are independent across sessions.

Treat graph expressions as trusted application configuration. Some FFmpeg
filters can read files, URLs, or other external resources. Endpoint validation
enforces the single-input/single-output PCM contract; it is not a sandbox and
does not make arbitrary graphs safe to expose to untrusted remote clients.
When no graph is configured, Remedia bypasses libavfilter entirely.

`position()` exposes three positions:

- `media` is the original source timeline associated with the latest output
  boundary. It can be estimated for timestamp-less media and for any graph that
  buffers or changes timing. The core does not infer speed ratios by parsing
  filter text.

- `submitted` is the end of the latest frame accepted by the output.
- `submitted` follows filtered PCM sample counts, not source time. This keeps
  Opus input contiguous even for tempo and sample-rate filters.
- `played` is an optional position reported by the output. It is `None` when an
  output can only report submission or buffering, and should not be interpreted
  as audible playback progress.

`NullOutput` consumes a frame immediately, so its played position follows its
consumed sample count. Its statistics distinguish scalar interleaved `f32`
values from sample frames per channel; duration is based on total consumed sample
frames, including audio consumed again after a seek.

FFmpeg may discard encoder-delay or padding samples described by a codec's
skip-sample metadata. Remedia sets the decoder packet time base from the
selected stream so FFmpeg can adjust decoded timestamps for those samples. The
messages “Could not update timestamps for skipped samples” and “Could not update
timestamps for discarded samples” are FFmpeg warnings about that timestamp
adjustment when the decoder lacks a usable packet time base; they do not mean
the decoder failed to apply the skip/discard metadata. Container duration may
therefore differ slightly from the number of audible decoded samples.

## Media output contract

Implement `MediaOutput` for an output consumer. Each session owns one output
instance. `write_frame` takes ownership of a `PcmFrame` and returns after that
frame is accepted. This synchronous call applies backpressure directly: while an
output is full, the session worker does not decode more audio. An output may use
its own buffer, but it must bound that buffer and honor cancellation.

Outputs implement `flush` to discard pre-seek audio, `pause` and `resume` for
downstream suspension, `finish` for natural end-of-stream, and thread-safe
`cancel` to interrupt an in-progress operation during stop or failure.
`played_position` may report a consumed/audible timeline; return `None` when the
output cannot provide one. The session holds no lock while calling output
methods.

Output methods execute on the playback worker, except `cancel`, which can run
concurrently to unblock them. A custom output must make `cancel` safe alongside
`write_frame`, `flush`, and `finish`. `stop()` waits for those methods to return
and then joins the worker. The current implementation uses one OS thread per
active session and does not introduce a global scheduler or real-time pacing.

## Structured diagnostics

`PlaybackSession::with_observability(handle)` attaches a session to the shared local tracing
dispatcher and metrics provider. Each playback start receives its own internal `playback_id`; events
include lifecycle transitions and failures without recording source paths or URLs. See the
[observability guide](/docs/observability/configuration) for subscriber ownership, event routing,
environment configuration, and OTLP export.

## Errors

Startup errors are returned from `play()`. Errors after startup set the state to
`Failed` and remain available from `last_error()`. `PlaybackError` distinguishes
decoder failures, output failures, invalid state operations, worker startup or
panic, cancellation, seek range errors, and unsupported seeking. The original
decoder or output error remains available as the error source where possible.

## Automatic Opus passthrough and PCM mode switching

When the output implements the optional `EncodedOpusOutput` capability (as
`OpusEncoderOutput` does), playback can route compatible source Opus packets
directly to the same packet sink used for encoded PCM. Other outputs remain
PCM-only and keep the regular decoder behavior. `PlaybackSession::processing_mode()`
reports the selected path as `Some(PlaybackProcessingMode::Passthrough)` or
`Some(PlaybackProcessingMode::Transcoding)` after source startup; it is `None`
before a source selects a path. The final selection remains inspectable after
completion.

Passthrough is enabled only when the selected stream is Opus at 48 kHz with a
supported mono/stereo family-zero OpusHead with zero pre-skip and output gain,
matching channel metadata, no initial/trailing padding, and packet payloads, durations, and sizes
accepted by the output. The packet duration is parsed from the Opus payload.
Packets with FFmpeg skip-sample side data or container duration indicating
trimming fall back to PCM. Active filtergraphs, any gain other than exactly
`1.0`, non-Opus input, seek, and outputs without encoded-Opus support require
transcoding. Unsupported input is a normal fallback. See [audio decoding](/docs/core/decoding)
for the complete conservative compatibility policy.

If a live filter or gain change cannot initialize the PCM decoder, the active
eligible passthrough path remains running and the filter update returns the
decoder error; the rejected graph is not retained. While playing, a gain change
that switches modes waits for the worker boundary and returns a transition
error. While paused, it stages the gain for resume. These operations can wait
for an in-flight input read or bounded output backpressure, and `stop()` cancels
the wait.

The demuxer stays open across mode changes. On passthrough-to-PCM activation,
the worker constructs the decoder from the selected stream parameters and
replays only a bounded history of up to 120 ms or 512 KiB of preceding Opus
packets. Warm-up output before the exact transition boundary is discarded;
the next unread source packet is then decoded and processed. This policy also
works with one-shot non-seekable streams and does not promise identical
warm-up behavior for every Opus implementation. The history is cleared on
seeking and source replacement.

When processing requirements are removed, the worker completes pending decoded
frames and any partial encoder PCM before forwarding the next source packet.
A remaining partial PCM block is padded to the shortest legal Opus packet
duration, adding at most 119 silent samples per channel, and the native encoder
state is reset before passthrough resumes. Delayed samples still buffered
inside the active filtergraph are discarded at this boundary, matching live
graph replacement behavior. No source is reopened, no output sink or Discord
sender is replaced, and no seek flush or RTP-generation change occurs. The
output sample position stays contiguous; RTP sequence and timestamp state
remain transport-owned. A short silence or transition artifact is possible,
especially around stateful or time-changing filters, so this is not a guarantee
of sample-perfect seamless audio.

Source-media position, processed PCM output position, and RTP transport time
remain separate. Passthrough packets receive the next contiguous output sample
position rather than inheriting container timestamps. Source timestamps still
drive the media position when available. Time-changing filters determine their
own output sample count; Remedia does not infer a speed ratio from graph text.

For a reproducible unpaced throughput comparison using an Opus file, run:

```sh
cargo run -p remedia-core --example opus_processing_benchmark -- ./media/track.ogg
```

The example reports the selected mode, wall time, delivered duration, packet
throughput, payload bytes, and real-time factor for automatic selection,
forced PCM re-encoding, a light filter, and a tempo filter. It measures an
in-process counting sink, not Discord network latency or peak memory.

## Opus encoding output

`OpusEncoderOutput` adapts normalized PCM to owned `EncodedOpusPacket` values and
passes them to an `OpusPacketSink`. The default packet duration is 20 ms (960
samples per channel at 48 kHz), stereo. It accumulates variable-sized decoder
frames and does not pace encoding. A final incomplete frame is zero-padded to
960 samples; packet metadata reports both the encoded duration and the shorter
amount of source audio represented. A seek drops partial PCM and resets the
native encoder before sending frames from the new timeline.

Each Opus output owns its encoder and sink. The sink contract is synchronous and
backpressured: implementations should use bounded storage and make `cancel`
safe alongside a blocked send. The adapter does not expose Discord types and can
be used with other packet consumers. Cargo builds libopus from bundled source
and statically links it; a system libopus development package is not required.

`OpusEncoderConfig::default()` explicitly selects 128000 **bits per second** (128 kbit/s for the
stereo stream), complexity 9, and variable bitrate (`vbr: true`). Higher bitrate generally improves
quality while using more bandwidth. Complexity 0–10 trades encoding CPU for quality; higher values
use more computation. VBR distributes bits according to audio complexity; disabling it requests
constant bitrate. The validated bitrate range is 500–512000 bits per second, following the
[libopus control documentation](https://www.opus-codec.org/docs/opus_api-1.5/group__opus__encoderctls.html).
The application mode remains `Application::Audio`.

Rust consumers can pass reusable settings to an output:

```rust
use remedia_core::{OpusEncoderConfig, OpusEncoderOutput, OpusPacketSink, OutputError};

fn configured_output(sink: impl OpusPacketSink) -> Result<OpusEncoderOutput, OutputError> {
    let config = OpusEncoderConfig {
        bitrate: 96_000,
        complexity: 5,
        ..Default::default()
    };
    OpusEncoderOutput::new_with_config(sink, config)
}
```

`config.validate()` checks ranges without creating libopus state. `new_with_config` validates
immediately; native allocation and control errors propagate on the first PCM write. Use
`new_with_config_and_observability(sink, config, handle)` to attach diagnostics as well. Existing
`new` and `new_with_observability` constructors use the defaults. Each output owns its configuration
and encoder; there are no global encoder settings. Seek resets retain the configured controls.

These controls apply only to PCM encoding. Compatible source Opus packets still pass through
unchanged without initializing libopus; their original bitrate and quality are unaffected. Filters
or gain that require PCM activate encoding with the output's settings. The server resolves settings
from [`audio.opus`](/docs/server/configuration#opus-encoder-settings); embedded Node.js uses core
defaults without a configuration file or a new JavaScript API.

## Runnable example

From the repository root, run:

```sh
cargo run -p remedia-core --example playback -- file ./media/track.wav
cargo run -p remedia-core --example playback -- url https://example.com/audio.mp3
```

The example prints metadata, state, submitted/played position, and null-output
statistics; it requests pause, attempts a midpoint seek, resumes, observes
completion, and stops the session. It reports unsupported seeking for sources
that cannot seek.

## Crossfade playback

Crossfade is disabled by default. Opted-in sessions can pass through eligible Opus
packets outside an overlap, and decode stereo 48 kHz PCM when mixing is required.
A whole packet must fit before the overlap boundary; otherwise the decoder warms
from bounded compressed history and trims to the exact source boundary. The sources
mix with a sample-accurate equal-power curve. One output and Opus encoder
remain open across promotions. Prepared sources keep their existing producer and
bounded PCM buffer after promotion; they continue transcoding rather than reopen
the source or bypass decoded samples. Direct sources can restore passthrough after
temporary volume processing only at matching source and encoder packet boundaries.
A gain update that leaves passthrough waits for PCM activation; restoration can
complete later when the direct source reaches a safe boundary.
Seeking disables passthrough restoration for that direct source. Ordinary sessions retain their existing Opus
passthrough selection and allocate no staging decoder or PCM buffer.

Defaults are a 5000 ms fade and a 30000 ms preparation lead. The engine emits
`prepareRequested` approximately 35000 ms before a known-duration source ends;
unknown-duration inputs do not receive end-based requests. Resolve upcoming sources
when requested rather than caching expiring URLs minutes ahead. Fades support
1000–30000 ms; preparation leads support 5000–120000 ms.

`stageNext(source, { expectedGeneration, entryId, queueRevision, sourceRevision })`
identifies a queued occurrence, including repeated tracks. Repeating the same
identity is idempotent. Higher queue revisions replace previous decisions; higher
source revisions refresh the same entry. Older revisions cannot overwrite a newer
stage, including after cancellation. Staging opens an independent decoder with a
bounded two-second PCM buffer and backpressure. `stageReady`, `stageFailed` and
`stageInvalidated` report its lifecycle.

At the fade boundary, an unready, missing, expired or failed stage is ignored and
ordinary source completion continues. The mixer never waits for an incoming frame;
an underflow during overlap cancels the transition and restores the outgoing
source. `transitionCancelled` identifies the interrupted incoming generation.
Pause freezes overlap progress and preserves preparation; resume checks readiness
and expiry. Seek clears preparation, advances the source generation to fence delayed requests,
and recalculates the request threshold. This generation change applies only to
crossfade sessions; the source is retained and no new start event is emitted. Stop
cancels decoders and blocked buffer operations. Volume and filters apply to the
mixed PCM; transport recovery retains the same playback engine.

The incoming source emits `playbackStarted` when overlap begins. After the fade,
the outgoing source emits `playbackCompleted` with
`continuation: { type: 'promoted', generation, entryId }`. That continuation means
the next source is already playing: consumers must not call `play()` for it.
The final source completes normally without continuation. Generations identify
sources independently of transport recovery and the continuous output clock.
