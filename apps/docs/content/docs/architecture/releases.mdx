## Release authorization

The release workflow accepts an exact `chore: release x.y.z` or `chore: release x.y.z-tag.n`
commit on `main`, either through a push or a manual workflow dispatch for that commit.
Only repository collaborators with current **write**, **maintain**, or **admin** access may
release. Both the original workflow actor and the actor initiating a rerun must qualify.
Commit author names and emails do not grant permission.

CI verifies access through GitHub's repository permission API before marking a run as a release,
and again before changing tags or drafts, uploading assets, publishing npm packages, or making
the GitHub release public. Missing identities, insufficient access, and API failures block release
actions. Normal pushes, pull requests, and manual dispatches without a release commit continue to
run their existing checks. Releases remain restricted to `main`.

## Build and validation

Fast lint, TypeScript and script checks run independently of native compilation.
A separate job validates Rust, source distribution and the documentation export.
Native integration uses the existing platform workflow. Low-level Rust, toolchain,
recipe and release infrastructure changes run all 13 addon targets and packaging;
TypeScript-only integration changes omit additional cross builds. Every release
runs the full target matrix and Node 22.18/24/26 coverage. PR native integration
uses Node 24. No supported release target is removed.

Ordinary Rust tests use the test profile. PR artifacts use an optimized `ci` profile
without LTO; distributed artifacts retain fat LTO based on measured build/size
tradeoffs. Server and addon builds share the same explicit Cargo target directory.
Compiled FFmpeg dependencies are cached by target, compiler and recipe inputs;
cache hits retain policy and final dependency audits. No bootstrap is compiled.

## Source and publication ordering

1. Authorize the actors and verify the immutable release tag before creating a draft.
2. Build and runtime-test the existing native targets, then pack and verify binaries.
3. Reuse or publish a hash-identified dependency source snapshot on this repository's
   source-only GitHub release. Add the small, exact Remedia source/configuration
   archive there using an immutable asset name. Source publication is authorized.
4. Upload missing binary draft assets; verify sizes and SHA-256 digests. Matching
   assets are preserved. A mismatched completed asset blocks the release.
5. Verify the complete corresponding source is public without authentication.
6. Publish original npm tarballs through OIDC in dependency order. Verify hashes
   before skipping any existing immutable version; wait for registry visibility and
   verify every package after publication.
7. Recheck draft assets and finalize GitHub only after npm succeeds. Publish GHCR
   afterward through the existing Docker workflow.

Retry failed jobs to resume an interrupted stage without rebuilding successful
native jobs. Upload retries reconcile accepted files before sending more data;
network errors include the failing operation and nested cause. Public binary
release assets are never overwritten. No new version is published by PR validation.

Source manifests, snapshots and instructions are described in
[licensing](/docs/licensing) and the distributed `SOURCE_DISTRIBUTION.md`. v0.3.0
retains its original assets. The source mechanism does not replace GPL obligations
with a lockfile or upstream URL list; automated audits do not establish legal
compliance. Android, Windows x86 and ARMv7 retain their experimental runtime status.
