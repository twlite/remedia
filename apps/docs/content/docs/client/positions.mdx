---
title: 'Playback positions and seeking'
description: Interpret source time, output time, unknown durations, and cached remote progress.
---

Use `session.position` to distinguish source progress from audio submitted to the output. All JavaScript positions are in milliseconds.

## Choose the right position

| Field                   | Meaning                                                                                 |
| ----------------------- | --------------------------------------------------------------------------------------- |
| `mediaMs`               | Original-source position associated with the latest accepted output boundary, or `null` |
| `mediaPositionAccuracy` | `timestamp`, `estimated`, or `null`                                                     |
| `submittedMs`           | Filtered PCM timeline submitted to the output                                           |
| `playedMs`              | Output-reported consumption, or `null` when unavailable                                 |

`durationMs` is `null` when the source has no known duration. Discord provides no audible sample-position report, so `playedMs` is `null`. Show approximate source progress rather than claiming listener-accurate playback.

```ts
await session.refresh(); // Request current state from a remote backend.
const { mediaMs, mediaPositionAccuracy } = session.position;
if (mediaMs !== null) {
  const approximate = mediaPositionAccuracy === 'estimated' || session.position.playedMs === null;
  console.log(`${approximate ? '~' : ''}${Math.floor(mediaMs / 1000)} seconds`);
}
```

## Read interpolated elapsed time

`session.getPlaybackTime()` returns the adapter's current elapsed-time estimate in milliseconds. Remote nodes extrapolate between authoritative events and snapshots with a monotonic clock, freeze while paused or disconnected, and reconcile after reconnect. A new source generation gets a new clock. Tempo filters mean source duration is not a valid upper bound for this estimate.

Use `position` when you need the source-versus-output distinction and accuracy metadata. Neither API measures Discord audibility.

## Understand filtered timelines

Tempo and buffering filters can change output sample counts independently of source time. `submittedMs` follows filtered samples. `mediaMs` stays on the source timeline and is marked estimated when timestamps or graph timing cannot establish an exact mapping. Remedia does not infer a fixed speed ratio by parsing graph text.

Remote positions are observations updated through events and `refresh()`. The SDK may use a local clock for preparation scheduling, but a cached position is not a continuously sampled audible clock. A standalone Node playback session uses a null output and may consume an entire file faster than real time.

## Seek within a source

```ts
await session.seek(30_000);
```

Files, owned buffers, and seekable HTTP resources can seek when FFmpeg's demuxer supports it. A seek resets the source and submitted timelines at the requested media time and drops queued pre-seek audio. It keeps the Discord connection.

Readable inputs and plugin media grants are forward-only. Forward seeking decodes and discards intervening audio. It can take time, and a position already passed by decoder read-ahead cannot be recovered. Backward seeks reject without stopping playback or flushing the active output.

### Fallback seeking

Some sources cannot seek: an HTTP origin that ignores range requests, a format without an index, or a plugin-hosted single-use stream. Create the session with `enableFallbackSeeking: true` and `seek()` serves them by opening a second decoder on the same track instead of rejecting. The current source keeps playing while the replacement decodes forward, then the two are swapped at one sample with a 5 ms blend. `seek()` resolves when the swap has happened, which can take several seconds for a distant position, so allow for that in your request timeout.

```ts
const session = client.createDiscordSession({
  guildId,
  channelId,
  userId,
  enableFallbackSeeking: true,
});
await session.seek(90_000); // resolves when the replacement is audible
```

Positions account for the preparation time. The replacement resumes at the requested position **plus the source time that played while it was prepared**: a seek to 90 s that takes three seconds resumes near 93 s. The offset stops while the session is paused and grows faster than wall-clock time under a tempo filter. The reported position jumps once at the swap and does not step backwards because of preparation latency.

`playbackSeeked` reports where the audio actually continues from:

```ts
session.on('playbackSeeked', (event) => {
  event.positionMs; // 93_000: applied. Use this for progress.
  event.requestedPositionMs; // 90_000: what was asked for
  event.fallback; // true: a replacement took over; the output timeline did not restart
  event.previousPositionMs;
});
```

For an ordinary seek `positionMs` equals `requestedPositionMs`. A fallback seek does not restart the output timeline, so the SDK's clock moves only the _media_ position to `positionMs` and keeps counting elapsed output time (`getPlaybackTime()`); `getMediaTime()` continues from the new position at the active tempo, so a session playing at `atempo=2` advances its media time twice as fast from 93 s. An ordinary seek restarts both at the target.

**Cancelling.** A newer `seek()` replaces one that is still preparing, and the older call rejects (`cancelled` on a remote node); so does a stop or a crossfade that begins first. You can also cancel one yourself:

```ts
const controller = new AbortController();
const seeking = session.seek(90_000, { signal: controller.signal });
controller.abort(); // rejects with the signal's reason; the seek can never apply later
```

The same happens when a remote node's request deadline (`requestTimeoutMs`, 15 s by default) passes: the SDK sends `player.seek.cancel` for the guild, so a seek the caller was told had failed does not apply afterwards. A seek already being applied when the cancel arrives cannot be stopped and finishes; its `playbackSeeked` event says so, which is how a caller that saw a timeout learns the position moved. Set `requestTimeoutMs` above the preparation time you expect (a distant seek on a slow origin takes as long as the transfer to the target).

Any failure, such as a source that cannot be reopened, a track that comes back different, or a target past its end, rejects while the original stream keeps playing. A one-shot `{ stream }` source cannot be reopened and still rejects; a plugin operation source is reopened by running its operation again, so the operation can run more than once for one track (see [plugin operations](/docs/server/plugin-operations#seeking-with-fallback-seeking)). A remote node must advertise `capabilities.fallbackSeeking.available`; a session that requests the option on a node that does not fails to start rather than silently ignoring it. After the swap an Opus stream is decoded and re-encoded for about 150 ms and then returns to forwarding packets.

Without the option, a rewind on a source that cannot seek is refused without touching the stream, and a failed seek never interrupts playback.

Seeking may invalidate a staged crossfade source and change its generation. Resolve a fresh stage in response to the next preparation request. For sample-level behavior, see [Rust seeking](/docs/core/playback#seeking-and-position) and [filter timing](/docs/core/filters).
