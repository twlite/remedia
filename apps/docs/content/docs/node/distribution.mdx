# Package distribution

The @remedia/node package contains the JavaScript loader, compiled TypeScript declarations, and
optional N-API platform packages generated by @napi-rs/cli. npm installs the platform package that
matches the current operating system and CPU. The loader does not download binaries during
installation.

## Release-tested platforms

The beta release pipeline includes these native packages after each target passes its native build, Rust tests,
binary inspection, and Node.js integration tests:

| Runtime target         | N-API package                 |
| ---------------------- | ----------------------------- |
| Linux x64 with glibc   | @remedia/node-linux-x64-gnu   |
| Linux ARM64 with glibc | @remedia/node-linux-arm64-gnu |
| macOS x64              | @remedia/node-darwin-x64      |
| macOS ARM64            | @remedia/node-darwin-arm64    |
| Windows x64 with MSVC  | @remedia/node-win32-x64-msvc  |

These release jobs run with Node.js 22.18, 24, and 26. The package declares Node.js 22.18 or newer.
The Node-API addon also has runtime tests for decoding and playback, addon loading, Discord voice
components, the embedded client, and the standalone server using the built server binary.

Additional npm platform packages are included by the current release packer:

| Target                     | Verification configured in CI                                         |
| -------------------------- | --------------------------------------------------------------------- |
| Linux x64 and ARM64 musl   | Cross-build with target FFmpeg 9; no native runtime integration tests |
| Linux ARMv7 hard-float GNU | Cross-build with target FFmpeg 9; no native runtime integration tests |
| Windows x86 and ARM64 MSVC | Cross-build with target FFmpeg 9; no native runtime integration tests |
| Android ARM64 and ARMv7    | NDK 27.2 / API 24 cross-build; no native runtime integration tests    |
| FreeBSD x64                | FreeBSD 15.1 VM build and native runtime integration tests            |

These describe workflow coverage, not confirmation that a particular release run passed.
The package gate requires all 13 configured addon artifacts. Only the five native runner targets
in the first table have standalone server release binaries. WASI is excluded.

## FFmpeg runtime libraries

Remedia links dynamically to FFmpeg 9. Install compatible FFmpeg 9 shared libraries on the runtime
machine before loading @remedia/node. npm installs the Remedia addon but does not install FFmpeg.
The addon expects these FFmpeg library ABI majors:

- libavcodec 63
- libavformat 63
- libavutil 61
- libavfilter 12
- libswresample 7

Linux GNU and macOS releases are linked against the matching shared FFmpeg libraries. Windows
requires the matching FFmpeg 9 DLLs and a compatible Microsoft Visual C++ v14 runtime. The Opus
encoder is built from bundled source and statically linked; a separate system Opus library is not
required. See the [FFmpeg 9 installation guide](/docs/node/ffmpeg-9) for platform-specific setup and the [Node.js bindings guide](/docs/node/bindings) for local build prerequisites.

The generated platform packages include os and cpu restrictions. Linux GNU and musl packages
also declare their matching libc value. These fields let npm select an appropriate package and
prevent a GNU addon from being installed as a musl addon.

## Client package

@remedia/client is pure TypeScript. It declares @remedia/node as an optional peer dependency for
embedded playback, so applications that use only remote server nodes can install the client without
the native package. During release packing, pnpm resolves this workspace peer dependency to the
actual released @remedia/node version.

## Install the public beta

```sh
npm install @remedia/node
# Remote-only consumers need only this package:
npm install @remedia/client
```

Both packages require Node.js 22.18.0 or newer and use ESM. See
[bindings](/docs/node/bindings) and [client configuration](/docs/client/overview) for API examples.

## Runtime discovery and troubleshooting

Install a shared FFmpeg **9** build matching the process CPU and OS/libc, including its transitive
shared dependencies. Having an `ffmpeg` executable on `PATH` alone is insufficient.

- Linux: install the libraries into the loader's configured directories (and update `ldconfig` when
  appropriate), or set `LD_LIBRARY_PATH=/path/to/ffmpeg9/lib` before starting Node or the server.
  FreeBSD also supports `LD_LIBRARY_PATH`, commonly with libraries under `/usr/local/lib`.
- macOS: use `brew install ffmpeg`; before launch set
  `DYLD_LIBRARY_PATH="$(brew --prefix ffmpeg)/lib"`. Mach-O install names may refer to the
  Homebrew prefix used at build time. Inspect with `otool -L`; a different prefix may require a
  local source build. Protected launch contexts may strip `DYLD_*` variables.
- Windows: add the directory containing `avcodec-63.dll`, `avformat-63.dll`, `avutil-61.dll`,
  `avfilter-12.dll`, `swresample-7.dll` and their dependencies to `PATH` before launch. Install
  the Microsoft Visual C++ v14 Redistributable matching the process architecture.
- Android: supply matching shared libraries in the application's native library search path;
  these packages have build-only verification and are not a tested Android deployment recipe.

For complete OS-specific installation examples, follow [installing FFmpeg 9](/docs/node/ffmpeg-9).\n\nFor `Cannot find native binding`, `ERR_DLOPEN_FAILED`, missing DLL, or missing shared-library
errors, check that optional npm dependencies are enabled and that the selected `@remedia/node-*`
package matches Node's architecture (`node -p process.arch`) and Linux libc. Reinstall with optional
dependencies enabled if necessary. Inspect linked libraries with `ldd` on Linux/FreeBSD,
`otool -L` on macOS, or `dumpbin /DEPENDENTS` on Windows; resolve every missing dependency and
restart with the loader environment set. ABI majors from another FFmpeg release are not substitutes;
do not rename or symlink incompatible major versions. `FFMPEG_DIR` and `PKG_CONFIG_PATH` are
build settings, not a runtime loader configuration. Source builds need development headers,
Rust, libclang, and the tools in the contributor guide.

## Licensing and distributed notices

FFmpeg libraries are installed independently and are not bundled with npm packages or server
binaries. Their licensing depends on the build selected by the user, including enabled components
and external libraries. GPL-enabled installations are not rejected. Users must comply with the
applicable licensing requirements; see [FFmpeg's official licensing information](https://ffmpeg.org/legal.html)
and [source](https://git.ffmpeg.org/ffmpeg.git). This is distinct from libopus, which is statically
included through `opus2`'s bundled backend, and other native Rust dependencies included in binaries.

Every npm package, including platform packages, contains `LICENSE` and `THIRD_PARTY_NOTICES.md` plus the `THIRD_PARTY_LICENSES.txt` appendix.
Standalone server releases include per-target `.tar.gz` archives with the executable and all three files,
as well as raw executables, all 13 `.node` addons, and accompanying notices.
Release assets are staged in a GitHub draft, which becomes public only after all npm packages
have been published successfully. Keep the notices with redistributed binaries.
See [licensing and media responsibility](/docs/licensing).

## Release authorization

The release workflow accepts an exact `chore: release x.y.z` or `chore: release x.y.z-tag.n`
commit on `main`, either through a push or a manual workflow dispatch for that commit.
Only repository collaborators with current **write**, **maintain**, or **admin** access may
release. Both the original workflow actor and the actor initiating a rerun must qualify;
commit author names and emails do not grant permission.

CI verifies access through GitHub's repository permission API before marking a run as a release,
and again before changing tags or drafts, uploading assets, publishing npm packages, or making
the GitHub release public. Missing identities, insufficient access, and API failures block release
actions. Normal pushes, pull requests, and manual dispatches without a release commit continue to
run their existing checks. Releases remain restricted to `main`.
