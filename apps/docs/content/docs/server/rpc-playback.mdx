## SDK channel movement and session configuration

The logical guild identity is `(clientSessionId, guildId)`; `channelId` is a mutable destination.
Different bot identities may own the same guild on the same server. The server does not enforce
cross-client uniqueness of `(botUserId, guildId)`. Applications must avoid competing controllers
for the same bot. Detached resumable sessions retain their ownership and resources until resumption,
explicit close, or expiry. No cross-client takeover or transport sharing is performed.

The SDK's `move(channelId)` uses existing `voice.suspend` and generation-fenced `voice.connect`
with the new channel and fresh Gateway credentials. It preserves the guild player and playback
generation. Movement uses the same protocol-v1 voice commands. Initial gain and filters use the existing
`player.volume.set` and `player.filter.set` commands before `player.play`. Configuration persists
across tracks and transport generations. Self-deaf and self-mute are Gateway OP 4 fields managed
by the application-side SDK, so they add no server wire fields. See the
[client session configuration guide](/docs/client/sessions#session-configuration-and-channel-movement).

## Media probing

After `client.create` or `client.resume`, an authenticated connection may send:

```json
{
  "version": 1,
  "id": "probe-1",
  "command": "media.probe",
  "params": {
    "source": { "type": "url", "url": "https://example.com/audio.mp3" },
    "timeoutMs": 15000
  }
}
```

File sources use `{"type":"file","path":"/allowed/audio.mp3"}` and resolve on the server. Operation sources are rejected with `invalid_request`: their media grants are single use, so probing would consume them.
Existing URL policy and file-root authorization apply. Bytes and client Readables are unsupported.
No guild ID, player or voice transport is involved. The result is the existing AudioStreamInfo
object: `streamIndex`, `codec`, `sampleRate`, `channels`, `channelLayout`, `durationMs`, `bitRate`,
and `metadata`. Unknown numeric fields are `null`. Missing tags are absent.

`timeoutMs` is optional, defaults to 15000 and must be an integer from 1 through 4294967295.
The configured RPC request timeout also applies. Native work runs on blocking workers, with at most
eight simultaneous probes server-wide and no waiting queue. Capacity errors use `resource_exhausted`.
Policy/parameter errors use `invalid_request`. Native errors use `media_failed`, `cancelled` or
`request_timeout`. Sources are closed immediately after inspection and never retained for playback.

To cancel an outstanding probe on the same connection, send `media.probe.cancel` with
`{"requestId":"probe-1"}`. It returns `{"cancelled":true}` even if the request already completed.
Socket disconnect, request timeout and cancellation interrupt the native operation. Blocking workers
retain their capacity permit until native cleanup finishes. FFmpeg discovery can consume source
bytes and estimate durations. It does not establish future playback availability.

## Fallback seeking

`node.info.capabilities.fallbackSeeking` is `{"available": true}` on a node that can replace a source
whose decoder cannot seek. Older nodes omit it; clients treat that as unavailable. It is a per-guild
opt-in: `guild.create` accepts `enableFallbackSeeking: true` (a boolean; anything else fails with
`invalid_request`). Omitted or `false` keeps the previous behavior, and the guild snapshot's
`fallbackSeeking` field reports the setting. No server policy gates it: the extra work is one
decoder and one connection for the duration of a seek, bounded as described in
[the core guide](/docs/core/playback#fallback-seeking).

With it enabled, `player.seek` on a source that cannot seek in place does not fail. The server
keeps playing, prepares a replacement and responds when it is audible. That takes seconds for a
distant target on a slow origin, which has consequences for the request:

**Where it landed.** The replacement resumes at the requested position **plus the source time that
elapsed while it was prepared**: a seek to 90 s that takes three seconds resumes near 93 s. Pausing
stops that clock, and a tempo filter speeds it up with the audio. The result and the `player.seeked`
event both say where the audio actually continues from:

| Field                 | Meaning                                                                                                                |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| `positionMs`          | `player.seeked`: the position the audio continues from (the applied position)                                          |
| `appliedPositionMs`   | `player.seek` result: the same value                                                                                   |
| `requestedPositionMs` | What the client asked for (both)                                                                                       |
| `fallback`            | `true` when a replacement source took over. The output timeline then continued; only the source position jumped (both) |
| `previousPositionMs`  | `player.seeked`: the source position before the seek                                                                   |

Crossfade guilds publish the same fields on the `player.seeked` they derive from the transition
timeline. `positionMs` equals the requested position for an ordinary seek.

**Deadlines and cancellation.** A seek never applies behind the client's back.

- If the request ends before the seek does (the deadline passes with `request_timeout`, or the
  connection drops), the server cancels the seek if it still can. A cancelled seek is guaranteed
  never to apply. One that is already being applied cannot be cancelled and announces itself with a
  `player.seeked` event when it finishes, so a `request_timeout` is always followed either by nothing
  or by that event.
- `player.seek.cancel` (`{guildId}`) cancels the guild's latest seek on demand and answers
  `{"cancelled": true|false}`: `true` means it will never apply, `false` that there was nothing to
  cancel or it was too late. The cancelled `player.seek` answers `cancelled`. It does not wait for
  the guild's lock, so it works while a seek is outstanding.
- Choose a client `requestTimeoutMs` above your expected preparation time. The client SDK sends
  `player.seek.cancel` itself when its deadline passes or an `AbortSignal` aborts.

**Concurrency.** The guild's playback lock covers submitting the seek only. Another `player.seek`,
`player.pause`, `player.stop`, `player.volume.set`, `player.filter.set` and `player.state`, and every
command for other guilds, are served while a seek prepares. Only the latest seek can replace the
source: an older one answers `cancelled`, and so does one that a crossfade began before. A seek still
waiting when the guild is stopped answers `invalid_state`.

**Failures** (the source could not be opened again, the reopened source is a different track, the
target is past its end, the origin did not catch up within 60 s) answer `unsupported`,
`playback_failed` or `invalid_state` and leave the original stream playing.

A plugin operation source is reopened by running its operation again on the same host, under the
same limits and media policy; see [Playing audio through plugins](/docs/server/plugin-operations#seeking-with-fallback-seeking).
A `file` or `url` source is reopened from the same, already authorized, location.

## Staged playback RPC

`node.info.capabilities.crossfade` reports policy, availability, defaults, the default `curve`
(`equalPower` unless the operator configured `adaptive`) and `curves`, the list of curves the server can mix:
`["equalPower", "adaptive"]`. Servers that predate the adaptive curve omit `curves`; clients treat that as
`["equalPower"]`. `guild.create` accepts optional
`crossfade: { enabled: true, durationMs: 5000, prepareBeforeMs: 30000, curve: 'adaptive' }`.
Server policy must allow it. `curve` is `equalPower` or `adaptive` (case sensitive) and defaults to the server's
configured curve; any other value fails with `invalid_request`. The guild snapshot's `crossfade.curve` reports
the curve in use. Omitted session options preserve ordinary playback.

`player.stage.next` accepts `guildId`, a file, URL or operation `source`,
`expectedGeneration`, `entryId`, `queueRevision`, `sourceRevision`, and optional
`expiresAtMs` (absolute Unix milliseconds). It returns a stage snapshot with
identity, `state`, `bufferedMs`, `source` metadata and nullable `error`. The client SDK exposes stream metadata as `info` in its `StageSnapshot`.
`player.stage.state` returns the current snapshot or null. `player.stage.clear`
cancels the pending stage. `player.prepare.ack` accepts `guildId` and
`expectedGeneration`, returning `acknowledged` and the current `generation`.
Acknowledgment is optional and never delays outgoing playback.

For an operation source, the operation runs before the stage is created and `expiresAtMs` is ignored,
because the node redeems the media immediately. A stage request whose `expectedGeneration` is already
stale fails with `stale_generation` before any operation runs. A pending preparation is superseded by a
newer `queueRevision`, or a newer `sourceRevision` for the same entry, and cancelled by
`player.stage.clear`, `player.stop`, a replacement `player.play`, guild destruction or shutdown. A result
that arrives after the generation changed is discarded with `stale_generation`.

Notifications are `player.prepare_requested`, `player.stage_ready`,
`player.stage_failed`, `player.stage_invalidated`, and `player.transition_cancelled`.
Preparation includes `remainingMs` and `transitionInMs`. Stage events carry queue
and source revisions. Incoming `player.started` includes
`transition: { type: 'crossfade', outgoingGeneration, entryId }`. Outgoing
`player.completed` includes `continuation: { type: 'promoted', generation, entryId }`
after the fade. The final source completes normally. Clients must reconcile the
promotion without sending a second `player.play`.

The server monitors these core events asynchronously. If the bounded core event queue overflows,
it emits `player.resynchronized` with a fresh `generation`, `droppedEvents`, and a full `snapshot`
in the same shape as `player.state`. `droppedEvents` includes both events evicted by the core queue
and retained events omitted while the server replaces partial history with that snapshot. Clients
should discard inferred transition history and apply the snapshot; if its `staged` field is null,
they may need to resolve and stage the next queue entry again. This notification is only emitted
for opted-in crossfade sessions after event loss.
