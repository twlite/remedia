## FFmpeg-independent commands

The standalone release contains two executables in the same directory:

- `remedia-server` is a lightweight CLI that does **not** link FFmpeg.
- `remedia-server-runtime` owns playback, WebSocket serving, and native FFmpeg 9 libraries.

These commands work without the FFmpeg shared libraries installed:

```sh
remedia-server --help
remedia-server --version
remedia-server --generate-config-file
remedia-server --list
remedia-server plugins list
remedia-server update
```

The CLI starts the native runtime for `serve` (including bare `remedia-server`) and `doctor`. On Unix, `serve` replaces the CLI process with the runtime so systemd, signals, and exit codes refer to the real server. On Windows, the CLI launches and waits for the runtime process.

`doctor` can run when FFmpeg is missing: the CLI starts and reports the native loader failure with installation guidance, rather than preventing all commands from starting. It still exits nonzero when the required runtime libraries are unavailable.

Both binaries are packaged in the release archive, and the installers put them side by side. Copying only `remedia-server` is sufficient for administrative commands, but `serve` requires the accompanying runtime binary. `REMEDIA_SERVER_RUNTIME` can override the native executable path for custom deployments.

The standalone executable is called `remedia-server`. The one-command installers also provide a shorter `remedia` launcher. Both accept the same options.

## Start a server

```sh
remedia-server
remedia-server serve --config ./remedia.config.json
remedia-server --config /etc/remedia/server.json
```

Running without a subcommand is equivalent to `serve`. The default configuration path is `./remedia.config.json`, relative to the process working directory. A configuration file is required, and its contents are validated before the WebSocket listener opens.

When supervising a child server through a pipe, pass `--shutdown-on-stdin-close` to
`serve` and keep its standard input open. Closing the pipe requests graceful shutdown:
active transfers and playback stop, resources are released, and the CLI waits for the
runtime to exit. This works on Windows as well as Unix. Input bytes are discarded;
EOF triggers shutdown. Without the flag, stdin does not control server lifetime.
On Windows, terminating the CLI with `SIGTERM` from Node.js forcibly kills it and does
not request graceful shutdown of its child runtime.

## Generate a configuration file

```sh
remedia-server --generate-config-file
remedia-server --generate-config-file ./server.json
```

The optional path defaults to `./remedia.config.json`. Generation refuses to overwrite an existing file. On Unix, the new file is created with mode `0600`.

The generated starter configuration uses loopback binding (`127.0.0.1:8787`), denies media file and URL sources by default, and references a password through `env('REMEDIA_RPC_PASSWORD')`. Supply that secret before starting the server. This intentionally differs from the repository's example configuration, which uses a sample media root and URL host.

## Manage plugin hosts

`plugins` registers remote [plugin hosts](/docs/server/plugins) in the `pluginHosts` section of your
configuration, so you do not have to edit the JSON by hand. The configuration file stays the only
source of truth: there is no separate database, lockfile or install directory.

<Callout title="Registering a host does not install code">
  A plugin host is an independent service built with `@remedia/plugin-host`. These commands only
  record where it is and which of its operations Remedia may run. Nothing is downloaded, built or
  executed, and uninstalling a host never touches the remote service.
</Callout>

The commands only edit configuration, so they work without FFmpeg and never start the server, the
playback runtime or any Discord connection. They honor `--config` (default `./remedia.config.json`),
`--env-file` and `--optional-env-file`, and they never create a configuration: if the file is missing
they point you to `--generate-config-file`.

| Command                                | Purpose                                                   |
| -------------------------------------- | --------------------------------------------------------- |
| `plugins install <url>`                | Discover a host and add it with the operations you choose |
| `plugins uninstall <host-id>`          | Remove the registration                                   |
| `plugins list [--json]`                | Show configured hosts (offline)                           |
| `plugins inspect <host-id>`            | Show one host's configuration; `--check` also contacts it |
| `plugins enable` / `disable <host-id>` | Turn a host on or off without deleting its configuration  |
| `plugins sync [host-id]`               | Compare the allowlist with what hosts advertise           |

Changes are written to the file, not to a running server. **Restart `remedia-server` to apply them.**

### Install a public host

```sh
remedia-server plugins install https://plugins.example.com
```

The command fetches `/.well-known/remedia`, validates it with the same rules the server uses, shows
the host and every `(pluginId, operation)` pair it advertises, and asks which to allow. The host ID is
the manifest's `hostId` when it declares one; otherwise it is derived from the display name or
hostname, or set with `--id`. A declared `hostId` always wins, and a conflicting `--id` is an error.
Existing registrations with the same ID or the same endpoint are refused.

Choose operations without prompts for scripts:

```sh
remedia-server plugins install https://plugins.example.com \
  --id media-host \
  --operation example.source/source.stream \
  --operation example.metadata/catalog.search \
  --yes
```

- `--operation PLUGIN/OPERATION` (repeatable) allows exactly those operations. The host must advertise them.
- `--all-operations` acknowledges and allows everything the host advertises.
- Without one of them a noninteractive session fails, because Remedia never enables advertised operations silently. Without `--yes` a noninteractive session also fails, because nothing is written unconfirmed.
- `--replay-safe PLUGIN/OPERATION` marks an allowed operation as safe to retry. It is off by default, and the host's own claims are never trusted: this is an operator decision.
- `--dry-run` prints the entry and validates the result without writing.

### Install an authenticated host

```sh
export REMEDIA_PLUGIN_TOKEN='a-long-random-token'
remedia-server plugins install https://plugins.example.com --token-env REMEDIA_PLUGIN_TOKEN
```

The file receives the reference, never the secret:

```json
{ "auth": { "type": "bearer", "token": "env('REMEDIA_PLUGIN_TOKEN')" } }
```

The variable is resolved with the usual precedence (process environment, then `--env-file` files) only
to authenticate discovery. Remedia does not create or modify `.env` files and never prints tokens. A host
that requires authentication, or rejects the token, produces an actionable error.

### Local and cleartext hosts

Security restrictions are the same as for a running server, and `--yes` does not relax them. HTTPS is
required unless you pass `--allow-insecure-http`, and loopback or private-network addresses need
`--allow-private-network`. Both opt-ins are written to the host's entry. URLs may not contain
credentials, paths, queries or fragments, redirects are never followed, and responses are size- and
time-bounded.

### List and inspect

```sh
remedia-server plugins list
remedia-server plugins list --json
remedia-server plugins inspect media-host
remedia-server plugins inspect media-host --check
```

`list` and `inspect` read only the file, so they show what is _configured_, not whether a host is
healthy. `inspect --check` contacts the host and reports protocol compatibility, authentication,
reachability and allowed operations which are no longer advertised. It exits with `2` when it finds a
problem. JSON output is stable and contains no credentials: a token appears only as the name of its
environment variable (`tokenEnv`) or as `"tokenSource": "inline"`.

### Enable and disable

```sh
remedia-server plugins disable media-host
remedia-server plugins enable media-host
```

A disabled host keeps its endpoint, credentials, operations and limits (`"enabled": false`), but the
server does not register it at startup: it is not discovered or listed, and requests naming it fail
with `plugin_host_disabled` instead of using another host. Omitting `enabled` means enabled.

### Synchronize

```sh
remedia-server plugins sync
remedia-server plugins sync media-host
remedia-server plugins sync media-host --apply
```

`sync` fetches each host's manifest and prints a diff: `-` marks allowed operations the host no longer
advertises, `+` marks newly advertised ones. By default it is read-only and exits with `2` when it
found differences or could not check a host. A host that is unreachable or incompatible is reported
and its configuration is left alone.

`--apply` asks about each change in an interactive session. Newly advertised operations are never
enabled implicitly, are added with `replaySafe: false`, and existing `replaySafe` values, identities
and authentication are never changed. For automation, name the changes explicitly:

```sh
remedia-server plugins sync media-host --apply \
  --add example.metadata/lyrics.search --remove-missing --yes
```

### Uninstall

```sh
remedia-server plugins uninstall media-host
remedia-server plugins uninstall media-host --yes
```

Shows the host and the operations being removed, then removes only that entry. Unrelated configuration
is untouched, the remote service is never contacted, and removing a host that is not configured is an
error. `--dry-run` previews the change.

### How the file is edited

Edits splice text into the file, so unrelated fields (including `$schema`), key order, indentation,
line endings and the trailing newline are preserved. The complete resulting configuration is validated
before anything is written; it is then written to a temporary file and renamed over the original. If
the file changed since it was read, nothing is written. Environment variables used by unrelated
settings do not need to be set to run these commands; they are checked for shape only.

Exit codes: `0` success, `1` failure, `2` for `sync` and `inspect --check` when they found something
that needs attention.

## Load dotenv files

```sh
remedia-server serve \
  --config ./remedia.config.json \
  --env-file .env \
  --optional-env-file .env.remedia
```

- `--env-file PATH` requires the file to exist, be readable, and contain valid dotenv assignments. Missing or malformed files are an error.
- `--optional-env-file PATH` skips a missing file, but unreadable or malformed existing files still cause an error.
- Both flags can be repeated. Required files are loaded first in argument order, then optional files in argument order. A later file entry overrides the same key in an earlier file.
- The already-defined process environment overrides any values loaded from files.

Supported input is `KEY=value`, optional `export KEY=value`, single/double-quoted strings, blank lines, and comments. Double quotes support `\\n`, `\\r`, `\\t`, `\\\\`, and `\\"`. File values are literal; no command execution, shell expansion, variable substitution, or `$KEY` interpolation occurs.

For example:

```dotenv
REMEDIA_RPC_PASSWORD='some-long-random-password'
REMEDIA_BIND_HOST=127.0.0.1
```

```json
{
  "bind": { "host": "env('REMEDIA_BIND_HOST')", "port": 8787 },
  "users": [{ "username": "media-bot", "password": "env('REMEDIA_RPC_PASSWORD')" }]
}
```

**Scope:** dotenv values are available to JSON `env('KEY')` references. Remedia does not mutate the process-global environment, so SDK or observability settings read directly from the process environment (including `REMEDIA_LOG` and `OTEL_*`) must be exported through your shell, container, or service manager.

The environment files may contain credentials. Limit their filesystem permissions and do not commit them to source control.

## Diagnose the server

```sh
remedia-server doctor --config ./remedia.config.json --env-file .env
```

The doctor prints the server version, OS and architecture, executable path, and the **actual loaded** FFmpeg library versions for avcodec, avformat, avutil, avfilter, and swresample. It compares their ABI majors with the FFmpeg 9 requirements (63, 63, 61, 12, 7). It also validates the selected JSON configuration with the loaded dotenv values. When `pluginHosts` are configured, it then performs a live discovery request to each endpoint and prints the host ID, state (`healthy`, `degraded` when an allowed operation is not advertised, or `unavailable`), the endpoint origin (never credentials), the number of advertised operations, and any discovery failure. An unreachable plugin host is reported but does not fail the command, because hosts may start after the node.

A failing ABI check or invalid configuration produces a non-zero exit status. Dynamic linker failures can still prevent the executable from starting at all; in that case, inspect installed libraries and loader search paths using your OS tools. Apart from configured plugin-host discovery, doctor does not test remote audio URLs, Discord credentials, or external network access.

## List running servers

```sh
remedia-server --list
remedia-server list
remedia-server --list --json
```

The table shows PID, bound listener address (including the actual port), active and maximum player/connection counts, resident memory where available, and processing/transport health. `--json` returns the raw live `node.stats` snapshot for each reachable server, plus its PID and listen address.

Each running process registers a private control endpoint on `127.0.0.1` and writes a secret-bearing discovery record under `~/.remedia/run`. Only the current operating-system user's records are scanned. Discovery requests are authenticated with a random token, have a short timeout, and return **status only**, never RPC credentials or media URLs. The control listener is unrelated to the user-facing WebSocket port and cannot operate or restart servers.

A server removes its record on graceful shutdown. If it crashes, a stale record can remain, but `--list` ignores records that do not answer the authenticated live query. This is local process discovery, not a global LAN scanner or process manager.

Resident memory currently uses Linux `/proc` data; macOS and Windows can report `n/a` until those platform metrics are implemented.

## Upgrade

```sh
remedia-server update
remedia-server upgrade
remedia-server update --no-ffmpeg
```

`upgrade` is an alias of `update`. It runs the verified platform installer embedded in the binary and defaults to the latest stable GitHub release, or the newest published prerelease if no stable release exists. Set `REMEDIA_VERSION` for an explicit release and `REMEDIA_INSTALL_DIR` for a custom install location.

The installer does not restart running server processes or manage services. Restart your service manually when ready. See [installation](/docs/server/installation) for the supported targets, FFmpeg requirements, checksums, and path setup.

## Build identity and updates

`remedia --version` and `remedia-server --version` show the embedded release version and Git
commit SHA. They also probe the separate native runtime for libavcodec, libavformat, libavutil,
libavfilter and libswresample versions. If the runtime or FFmpeg is missing, the build identity
still prints and the command succeeds with an unavailable-libraries message.
The server uses the same embedded version in `node.info` and `node.stats`, with an additional
`commit` field. Existing protocol fields are unchanged.

Release CI embeds the selected release version and checkout SHA. Local Cargo builds use the
nearest `v` release tag and current commit, falling back to the Cargo package version and
`unknown` outside Git. Source archive builders can set `REMEDIA_BUILD_VERSION` and
`REMEDIA_BUILD_COMMIT` at build time.

`remedia update` runs the bundled platform installer. Both installers compare the full selected
version, including prerelease identifiers, before downloading any artifacts. An identical version
prints “already current” and succeeds without replacing files or provisioning FFmpeg. Different
selected versions are installed, including dev-to-stable transitions and explicitly selected
older versions. `latest` selects GitHub's stable release, falling back to a prerelease only when
no stable release exists. Use the installer's FFmpeg-only mode to repair dependencies separately.
