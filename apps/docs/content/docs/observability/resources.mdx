# Process resources

`node.stats` keeps its existing `cpu`, `memory`, player, connection, and health
fields. The additive `resources` object contains the same CPU and memory counters,
`collectedAtUnixMs`, `cpuSampleIntervalMs`, `samplingIntervalMs`,
`collectionDurationMs`, and `openHandles`. `playback.activeSessions` counts sources
in active lifecycle states, including paused and stopping sources; it is not an OS
thread count. `players.active` remains allocated guild players, and
`players.available` is the configured maximum minus allocated players, clamped at zero.

`@remedia/client` exposes typed `ResourceMemory`, `ResourceCpu`, and
`ProcessResourceStatistics` through node statistics, along with `playersAvailable` and `playbackActive`. Existing servers may omit new
fields; clients keep them optional and report absent `resources` as null. Existing
RPC fields remain compatible. No additional endpoint or authentication mechanism
is introduced. Local `remedia-server --list` displays private resident memory where
available, otherwise explicitly labeled macOS footprint, alongside RSS.
`--list --json` retains the full statistics object and discovery security checks.

## Memory accounting

All memory counters are **bytes**, independent and nonadditive. Null means
unsupported, inaccessible, or not yet sampled. No counter substitutes for another.

| Counter                     | Linux                                                     | macOS                                | Windows                                                    |
| --------------------------- | --------------------------------------------------------- | ------------------------------------ | ---------------------------------------------------------- |
| `residentBytes`             | smaps rollup RSS; status VmRSS fallback                   | Mach resident size; libproc fallback | WorkingSetSize                                             |
| `privateResidentBytes`      | Private_Clean + Private_Dirty in smaps rollup (USS-style) | null                                 | EX2 PrivateWorkingSetSize when supported                   |
| `proportionalResidentBytes` | smaps rollup PSS                                          | null                                 | null                                                       |
| `committedPrivateBytes`     | null                                                      | null                                 | PrivateUsage (commit, including nonresident pages)         |
| `virtualBytes`              | status VmSize                                             | Mach virtual size                    | VirtualQuery mapped/reserved regions, excluding free holes |
| `reservedVirtualBytes`      | null                                                      | null                                 | VirtualQuery MEM_RESERVE regions only                      |
| `peakResidentBytes`         | status VmHWM                                              | Mach resident size peak              | PeakWorkingSetSize                                         |
| `footprintBytes`            | null                                                      | Mach phys_footprint                  | null                                                       |

Linux rollup collection requires kernel support and permission; losing access
makes USS and PSS null while status can still supply RSS. These counters describe
the process inside its current namespace, not cgroup usage or a container memory
limit. Private hugetlb accounting is not added to the stated clean/dirty metric.

macOS footprint includes platform-specific ledger accounting and compressed memory;
it is not USS. The collector does not infer private resident memory from Mach's
`internal` counter or subtract shared libraries from RSS. A reliable USS/PSS counter
is unavailable through the implemented task snapshot, so these fields remain null.

Windows EX2 private working set needs a sufficiently recent Windows release.
If EX2 fails, the collector falls back to EX for RSS, peak RSS, and private commit,
leaving private resident null. Reserved virtual addresses are not resident RAM.
Other target operating systems return null memory fields until a native backend
is implemented; available parallelism remains available where Rust supports it.

## CPU and sampling

`cpu.processPercent` is the difference in cumulative process user + system CPU
milliseconds divided by elapsed wall milliseconds, multiplied by 100. **100% is
one logical CPU** and multithreaded processes can exceed 100%. It is null until two
samples exist. `userTimeMs` and `systemTimeMs` are cumulative milliseconds.
`availableParallelism` is Rust's platform estimate. `threadCount` counts actual OS
threads, including the short-lived collector when it samples itself.
`loadAverage1m` is the Unix system load average, not process utilization. Unsupported
platform counters are null. `openHandles` counts Unix descriptors or Windows
process handles; Linux excludes the collector's own directory enumeration handle.

A process-wide cache refreshes on demand after **1000 ms**. Every caller immediately
gets the previous completed snapshot while at most one background collector runs.
The first call may return a snapshot with null timestamp and counters. Infrequent
requests produce longer CPU measurement intervals; there is no periodic collector
when nobody requests statistics. Sampling timestamps and duration make staleness
and collection cost visible. Expensive OS queries run off Tokio and audio workers.

## Embedded mode

```ts
import { Remedia } from '@remedia/node';

const remedia = await Remedia.create();
try {
  const resources = remedia.processResources();
  console.log(resources.memory.privateResidentBytes, resources.memory.footprintBytes);
} finally {
  await remedia.close();
}
```

This synchronous method reads the native cache and schedules refresh without
blocking JavaScript on collection. Embedded client node snapshots use it when the
native addon supports it; older addons retain empty CPU/memory objects and null
resources. Every embedded instance in one Node.js process shares the process
measurements, including memory owned by JavaScript, libraries, and other instances.
They are not measurements of an individual Remedia engine or JavaScript heap.
